## 0. 目标、范围与方案

### 0.1 目标

在本项目（UE 5.8 源码版，RTX 5080）里还原 Atmos 的四季动态天气：天气由物理模拟决定，所有系统读同一份天气、同一个风，季节随时间推进。
先在新建的小关卡 `L_WeatherLab` 验收，通过后放进 2 km 的山谷 `L_PyWorld`。

**成功标准**：

1. 第 2–7 节的验收表全部通过；能量化的项目由第 8 节的测试自动检查。
2. 按天气状态计算的 GPU 预算达标（§1.7）。
3. 每个里程碑的截图集和录音经用户评审通过。

### 0.2 范围

**做（14 项）**

- 天气核心：区域物理天气模拟；统一风场 + 喷溅粒子；云、雨雪与雷暴；氛围图（编排层）。
- 地表天气：雨湿与积水；积雪与融化；深雪变形；室内 / 屋檐遮挡。
- 四季：昼夜与季节日照；植被四季外观；多状态物体；季节推进与气候。
- 联动：角色（头发、衣服随风，淋湿、落雪）；天气声音。

**不做**：NPC 感知受天气影响；人群与动物的反应。

### 0.3 选定方案

| 决定 | 选择 |
|---|---|
| 技术路线 | C++ 运行时插件 + GPU 计算（RDG）；湿、积水、积雪用 base pass 之后的延迟 GBuffer pass；StateTree + 数据资产做编排；纯 Python（numpy）参考模型做离线测试 |
| 模拟保真度 | 3D 网格（Stormscapes 简化版），8 × 8 km、高 8 km |
| 季节推进 | 离散换季，切换时有过渡 |
| 验收场景 | 先在新建的小关卡验收，再放进 L_PyWorld |
| 树的风 | PVE（Procedural Vegetation Editor）导出的 Dynamic Wind 骨骼树，加我们改造的 Transform Provider |
| 角色 | MetaHuman 做发丝，Chaos Cloth 做衣服 |

### 0.4 前提与约束

- **引擎不改**。用到的实验功能（Dynamic Wind 标注"极度实验"、PVE、Nanite 体素植被、MeshPartition）都包在我们自己的接口后面，
  出问题只换一处。
- **光照**：用 Lumen 实时 GI，不做原作那种按季节准备的烘焙光照数据。
- **平台**：单人、单视图、Windows 桌面（SM6 显卡）。不做联网同步、分屏优化和移动端。
- **区域**：v1 的模拟区域固定在关卡中心，适用于不超过约 4 km 的关卡。跟随玩家滚动的区域以后再做，数据布局先预留。
- **默认参数**：1 游戏日 = 1 真实小时；每季 7 个游戏日；纬度 35°N（原作的伊贺）。三者都是参数。
- **性能口径**：在 1440p 内部分辨率（TSR）下测量。
- **运行时机**：PIE、Simulate 和游戏里默认运行。编辑器视口里默认暂停，可在调试面板里打开，摆场景时配合手动覆盖使用。
- **存档**：项目没有存档系统。天气提供 `SaveWeatherState` / `LoadWeatherState` 接口（一个 `USaveGame` 子类），由游戏决定何时调用；内容见 §1.9。
- **编译**：编译 C++ 前关掉 PCG_Codex 编辑器。它的 Live Coding 互斥锁和 NetCore DLL 会挡住本项目的编译（拆解文档 §6.6）。

## 1. 总体架构

### 1.1 核心决定：中间放一层"天气场"

大气模拟只负责写天气场，手动覆盖也能直接写。云、风、地表、粒子、植被、角色、声音只读天气场和编排器输出的参数，不直接依赖模拟。
所以每个表现系统都能先用手动天气单独做、单独测；模拟接进来时，也有现成的画面检验它。

### 1.2 三层、八个部件

| 层 | 部件 | 职责 | 实现 | 节 |
|---|---|---|---|---|
| 模拟 | 时钟与日历 | 时间、日期、季节和换季过渡；太阳、月亮的位置随纬度和日期变化 | C++ | 6 |
| | 大气模拟（Atmos） | 关卡上方的 3D 网格：风、温度、水汽、云水、雨雪，含地形阻挡；每季气候作为边界条件 | GPU compute，另有 numpy 参考模型 | 2 |
| | 近场风 | 相机周围 256 × 256 × 64 m 的 3D 风，绕过地形和建筑；边界取自模拟的粗风 | GPU compute | 3 |
| 编排 | 编排器（对应 Anvil 的氛围图） | 天气型和季节两个状态机；把天气映射到灯光、雾、后期、云、粒子、声音、植被季节的参数；调度阵风和闪电 | StateTree + 数据资产 | 1.5 |
| 表现 | 地表天气 | 湿、积水、积雪、结冰随时间累积和消退；base pass 后改写 GBuffer；屋顶和室内遮挡；深雪变形 | GPU compute + 延迟 pass + Nanite tessellation | 4 |
| | 云与降水 | 体积云读 Atmos 的体积；雨、雪、溅落、闪电；雾 | 云材质 + Niagara | 5 |
| | 植被与季节物体 | PVE 骨骼树（改造的 Dynamic Wind 读风场）；草用 WPO；换季时换材质或换网格；冰柱、冰面等多状态物体 | PCG + 组件 | 3、6 |
| | 角色与声音 | 发丝和布料随风，湿身和落雪；雨、风、雷、脚步，区分室内外 | MetaHuman + Chaos Cloth + MetaSounds | 7 |

### 1.3 共享数据

部件之间只通过两类共享数据交流：GPU 上的天气场，以及 CPU 上的摘要和参数总线。所有分辨率和更新频率都是参数，写在 §2.6 的 JSON 里。

**GPU 天气场**

| 天气场 | 格式 | 写入方 | 读取方 |
|---|---|---|---|
| Atmos 体积 | 128 × 128 × 32，RGBA16F：云水、降水（雨 + 雪）、冰的比例、上升速度 | Atmos | 云材质 |
| 粗风 | 128 × 128 × 32，RGBA16F：u、v、w | Atmos 或手动覆盖 | 近场风的边界；近场窗口外的风 |
| 地面图 | 128 × 128，多通道：降水率、雨雪比例、近地面气温、湿度与雾、近地面风、雷暴潜势、云量 | Atmos 或手动覆盖 | 地表状态、降水粒子、角色、声音、编排器 |
| 近场风 | 128 × 128 × 32（2 m 一格），RGBA16F：风速 xyz、湍流强度；另附一张 128² 的地面高度，用于贴地坐标换算 | 近场风 | 树、草、粒子、发丝、探针 |
| 阵风图 | 2D，覆盖关卡，8 m 一格（L_PyWorld 256²） | 编排器的阵风事件 | 近场窗口外的草 |
| 远景天气图 | 2D，约 128 × 128 km，512²（250 m 一格）：覆盖率、云型、降水 | 编排器（按天气型） | 云材质 |
| 地表状态 | 覆盖关卡，1 m 一格，RGBA16F：表面湿度、积水深度、积雪水当量、结冰比例 | 地表模型 | 延迟 pass、地形材质、角色、声音 |
| 树冠与杂项状态 | 覆盖关卡，4 m 一格，RGBA16F：叶面湿度、叶上积雪、雪龄、落叶量 | 地表模型 | 延迟 pass |
| 压痕图 | 相机周围约 50 m，5 cm 一像素（1024²） | 压印器 | 地形材质（深雪） |
| 定向雨深度 | 沿雨方向的正交深度，覆盖约 40 m，512² | 降水系统 | 雨雪粒子 |
| 烘焙（每关） | 1 m：地形高度、实体高度、冠层顶高与疏密、地表类型、积水潜力、水面高度、美术遮罩；另有 Atmos 用的 62.5 m 地表纹理 | `weather.py bake` | 几乎所有部件 |

材质参数集不能放纹理，所以材质直接引用这些渲染目标资产；坐标映射（原点、尺寸）通过 `MPC_Weather` 传。

**CPU 侧**

- **摘要**（约每秒一次）：玩家所在处的气温、降水、风、云量、对流强度、当前天气型；全域云量、0 °C 层高度。
- **探针**：最多 64 个点，GPU 每帧采样，2–3 帧后回读。供衣服、头发、风声和玩法查询使用。
- **CPU 副本**：
  - 地面图，每秒回读一次；
  - 烘焙的实体高度（约 8 MB），加载关卡时读入，供角色和声音做遮挡判断；
  - 玩家周围 32 × 32 m 的地表状态，每秒回读 2 次。
- **参数总线**：编排器输出的命名参数，写到 `MPC_Weather`、灯光、雾、天空、后期、Niagara 和音频控制总线。

**`MPC_Weather`** 存放：
- 各天气场的坐标映射；
- 四个季节的混合权重；
- 时刻，以及太阳和月亮；
- 相机处的风和降水；
- 闪电闪光（位置、强度、半径）；
- 全局的风和地表系数。

### 1.4 数据流

```
时钟/日历、每季气候表 → 编排器（天气型序列）→ Atmos 的边界与外部驱动
Atmos（GPU，按游戏时钟步进，分帧执行）→ Atmos 体积、粗风、地面图 ← 手动覆盖（测试和美术用）
Atmos 体积 + 远景天气图 → 体积云
粗风 + 阵风事件 + 烘焙 → 近场风 → 树、草、粒子、发丝、布料、探针
地面图 + 近地面风 + 烘焙 → 地表状态 → 延迟 GBuffer pass（每帧）、地形材质
地面图 → 降水粒子、闪电调度（雷暴潜势）
摘要（约每秒）→ 编排器 → 参数总线 → 灯光、雾、后期、声音、植被季节
地表积雪 → Atmos 地面反照率（反馈）
```

### 1.5 编排器（对应原作的氛围图）

- **两个并行状态机**（StateTree）：
  - **天气型**：
    - 按气候表抽出天气型序列，美术和关卡也可以指定或锁定某个天气型。
    - 每段持续几个游戏小时。切换以锋面的形式从上风方向扫过来，经过 1–3 个游戏小时（§5.2）。
  - **季节**：四个季节状态，加四个过渡状态（§6.5）。
- **数据资产**：
  - `DA_Climate`：每关一份，按季节分表（§6.2）。
  - `DA_WeatherType`：边界和外部驱动参数，以及灯光、雾、调色的预设。
  - `DA_SeasonLook`：各季节的调色和植被材质实例。
  - `DA_WeatherVariant`：多状态物体（§6.4）。
- **事件调度**：
  - 阵风事件（§3.2）；
  - 闪电（§5.5）；
  - 喷溅粒子的生成率（§3.5）。
- **参数映射**：把天气、季节、时刻映射到灯光强度、天光、高度雾、调色、云参数、粒子、声音和植被季节。
- **手动覆盖**：
  - 可以按场单独覆盖降水、风、气温、云、地表状态，取均匀值或画出来的分布。
  - 随时可用。M0–M2 还没有 Atmos，它是唯一的天气来源。

### 1.7 性能预算

天气相关的 GPU 开销按天气状态计算：雨和深雪不会同时出现，所以不把所有项相加。体积云单独计算。

| 项 | 预算 | 何时有 | 节 |
|---|---|---|---|
| Atmos | 平均每帧 ≤ 0.2 ms（每步 ≤ 1 ms） | 一直 | 2 |
| 近场风 | 平均每帧 ≤ 0.15 ms | 一直 | 3 |
| 树的风 | ≤ 0.2 ms（约 10 个树模型） | 一直 | 3 |
| 草的风采样 | ≤ 0.2 ms | 一直 | 3 |
| 喷溅粒子 | ≤ 0.2 ms | 有风时 | 3 |
| 延迟 pass | ≤ 0.3 ms | 一直 | 4 |
| 地表状态更新 | ≤ 0.05 ms | 一直 | 4 |
| 深雪（压痕 0.05 + tessellation 0.3） | ≤ 0.35 ms | 有积雪时 | 4 |
| 雨（粒子、雨层、溅落、定向深度捕获） | ≤ 0.5 ms | 雨天、雷暴 | 5 |
| 雪粒子 | ≤ 0.3 ms | 雪天 | 5 |
| 角色叠加材质 | 每个近处角色 ≤ 0.1 ms | 有近处角色时 | 7 |
| 换季过渡的峰值 | 每帧 ≤ 0.5 ms | 过渡期 | 6 |
| 体积云（单独计） | ≤ 2.5 ms | 一直 | 5 |

| 天气状态 | 合计（不含云） |
|---|---|
| 所有状态共有：Atmos、风、延迟 pass、地表状态 | 1.3 ms |
| 雨、雷暴（含一个近处角色） | 约 1.9 ms |
| 雪（含一个近处角色） | 约 2.05 ms，略超 2 ms 的目标；M5 实测后决定压缩哪一项 |

各项都是估计，以实测为准。超出预算的项由第 8 节的性能测试指出。

## 2. 大气模拟（Atmos）

### 2.1 输出

- **Atmos 体积**（RGBA）：云水、降水、冰的比例、上升速度。云材质读它（§5.2）。
- **粗风**（3D）：近场风的边界，也是近场窗口外的风（§3.1）。
- **地面图**（2D）：降水率、雨雪比例、近地面气温、湿度与雾、近地面风、雷暴潜势、云量。
- **摘要**：约每秒回读一次（§1.3）。

### 2.2 两个尺度

8 km 的盒子里长不出锋面这类大范围天气系统。只靠它，天气会一直重复同一种局部对流，而且没法控制。所以分两层：

1. **天气型（大尺度）**：
   - 由编排器按每季的气候表推进，类型有晴、晴天积云、阴（层云）、锋面雨、雷暴、雾、雪、暴风雪。
   - 天气型本身不画任何东西，只给模拟设定边界条件和外部驱动：吹进来的空气的温湿度随高度分布、风向风速，以及大尺度抬升
     （锋面带来的整片层云和连续降水靠它）。
   - 季节改变来流的温湿度廓线：冬天空气冷，降水落下来就是雪。
2. **3D 模拟（局部）**：在这些条件下自己算出云在哪里长、雨下在哪里、风怎么绕山。

原作也是这样搭的：宣传片原话是"天气状态 + Atmos + 喷溅粒子"。Stormscapes 也用少量高层控制量驱动，并且可以接实时气象数据。

### 2.3 网格与区域

- **大小**：8 × 8 km、高 8 km。
  - 水平 128 × 128，每格 62.5 m。
  - 竖直 32 层：近地面约 60 m 一层，按约 1.08 的比例往上逐渐变疏，到顶约 650 m，因为近地面要能分辨雾和地形。
  - 共约 52 万个格子。
- **位置**：固定在关卡中心。L_PyWorld 是 2 km 见方，四周还能留出 3 km 给来流。
- **地表数据**：每关烘焙一次（§4.6），包括：
  - 地形高度：地下的格子当实体处理；
  - 水体：作为蒸发源；
  - 植被覆盖：决定蒸腾量和地面粗糙度。
- **顶部**：最上面 1 km 是吸收层，防止波从顶部反射回来。

### 2.4 物理模型（Stormscapes 简化版）

状态量：风（u、v、w）、位温、水汽、云水、雨、雪。每一步依次做下面五件事：

1. **平流**：半拉格朗日方法加误差补偿（BFECC / MacCormack），保住云的清晰边缘。
2. **受力**：
   - 浮力由虚位温偏差减去云和雨雪的重量算出，不是人为给定；
   - 风向天气型的背景风缓慢回拉；
   - 地形是实体边界，气流越山时自然被抬升。
3. **气压投影**：多重网格解泊松方程，用上一步的结果热启动，让风场无散。
4. **微物理**：
   - 饱和比湿用 Tetens / Magnus 公式；过饱和就凝结成云并放出潜热，云因此会自己往上长；不饱和就蒸发。
   - 云水多到一定程度转成雨（Kessler 式自动转化，加上雨滴碰并云滴）。
   - 0 °C 以下生成雪，雪落过暖层融成雨，同时吸热。
   - 雨在云下的干空气里蒸发降温，形成下沉气流，也就是暴雨前的那阵风。
   - 雨约 6 m/s、雪约 1 m/s 下落，落地的量写进地面图。
5. **地表交换**：
   - 白天按太阳高度和云的遮挡加热地面，所以午后会起对流云；云的遮挡由模拟按每一柱的云水自己算出。
   - 夜间地面降温，山谷里起早雾。
   - 水面和植被按温度和风速蒸发水汽，对应宣传片说的"夏日阳光蒸发水、水汽上升成云、最后下成雨"。
   - 地表的积雪（§4）提高反照率，雪地上方的空气更冷。

**雷暴**：不模拟电荷，用"上升气流强度 × 云厚 × 是否有冰相"算雷暴潜势，编排器据此调度闪电。冰雹、霰和电荷都不做。

### 2.5 时间与运行方式

- **跟随游戏时钟**：模拟时间按游戏时钟的倍率推进。1 游戏日 = 1 真实小时时，每真实秒推进约 24 秒模拟时间（约 8 步，每步约 3 s），
  一团积云在几分钟真实时间里长成。调试时可以快进。
- **分帧执行**：
  - 每步拆成几个阶段，分到连续几帧执行：平流一帧，压力迭代两三帧，微物理和输出一帧。
  - 每步不超过 1 ms，平均每帧不超过 0.2 ms。
  - 输出双缓冲，读取方在最近两个完整状态之间插值，所以云的移动是平滑的。
- **加载**：加载关卡或读档时，先快速预跑约 1 小时模拟时间（约 1–2 s），避免开局天空一片空白。
- **稳健性**：
  - 水汽、云、雨雪的含量限制为非负，风速设上限；
  - 调试版每秒回读一次各量的最大值和最小值，用来查数值异常；
  - 手动覆盖随时可用。

### 2.6 参数

- **一份 JSON**：物理常数和调参值都放在 `Tools/weather` 下的同一份 JSON 里，C++ 和 numpy 参考模型读的是同一份。近场风（§3）的参数也在这里。
- **结构校验**：有一个测试检查两边读的键是否一致（§8.2）。

### 2.7 验收（M3）

| 场景 | 预期 |
|---|---|
| 干燥稳定的大气 | 不起云 |
| 一团暖湿空气 | 长成积云，云底高度符合抬升凝结高度（约 125 m × 气温与露点之差） |
| 气流越山 | 迎风坡起云下雨，背风坡少雨 |
| 夏日午后 | 地面加热，长出对流云并下阵雨，傍晚消散 |
| 冬季 | 同样的湿度下下雪；0 °C 层上下雨雪转换 |
| 水量守恒 | 总水量的变化 = 地面蒸发 − 落地雨雪，误差 < 1% |
| 性能 | 每步 ≤ 1 ms，平均每帧 ≤ 0.2 ms |

## 3. 风

### 3.1 两层风，一个出口

- **粗风**：Atmos 的风，62.5 m 一格，几秒一步。负责大范围的风：风向风速随高度的变化、越山、雷暴的外流。
- **近场风**：相机周围 256 × 256 × 64 m 的细网格，2 m 一格（128 × 128 × 32）。负责局部的风：
  房子和墙后的背风区、顺着街道的穿堂风、林子里风小、一阵阵扫过的阵风。
- **一个出口**：树、草、粒子、旗子、水面、角色、声音都从同一处取风。
  - 在近场窗口内取近场风；窗口外取粗风，再叠一张 2D 阵风图；窗口边缘 16 m 内平滑过渡。
  - GPU 上的入口是材质函数 `MF_WeatherWind` 和 Niagara 模块 `NM_WeatherWind`；CPU 上的入口是探针。

### 3.2 近场风模拟

- **求解器**：复用 Atmos 的流体代码（平流 + 多重网格压力投影），去掉水汽和热力学，只算风。
- **窗口**：
  - 跟着相机走。平移时数据不搬动（环形寻址），只把新露出的那一条格子用粗风初始化。
  - 竖直方向贴地：每一列从当地地面算起 32 层，所以坡上的树和房子都在网格里。
- **输入**：
  - **粗风**：插值到近场，近地面按对数风廓线补齐，粗糙度看地表类型（草地小，树林和城镇大）。迎风的边界当来流；
    内部也缓慢地往粗风拉，时间常数 30–60 s，这样局部效果留得住，大范围的风又跟着 Atmos 走。
  - **湍流**：来流里叠一块预先生成的湍流场（Python 工具生成，无散，可平铺），强度由天气型和 Atmos 的不稳定程度决定。
  - **阵风事件**：
    - 编排器按天气型的阵风频率排出来；雷暴时由 Atmos 的下沉气流给出方向和强度。
    - 一次阵风是一团 50–150 m 宽、持续 5–20 s 的速度脉冲，从上风边界进来，随风穿过窗口，被障碍物挡住或绕开。
    - 窗口外用同一批事件画阵风图，远处的草也有风浪。
  - **局部风源**：爆炸、马匹掠过之类，只留接口，v1 不接玩法。
- **障碍物**（来自 §4.6 的烘焙）：
  - **实体**：实体高度以下的格子当实体处理。这是 2.5D 的简化，算不出桥洞、拱门里的风，对效果影响不大。
  - **冠层**：不算实体，算透风的阻力，大小正比于疏密 × 风速²。所以林子里风小、林冠上方风大。冬天落叶后阻力降到约 1/4，
    林子里的风更大。
- **步进**：
  - 固定 15 Hz：20 m/s 的大风每步也只走 0.67 格。
  - 每步估计约 0.4 ms，拆到 4 帧执行，平均每帧不超过 0.15 ms。
  - 输出每帧插值成一张"当前风"体纹理。
- **时间线**：M2 时还没有 Atmos，粗风先由天气型或手动覆盖给一个均匀风。

### 3.3 树：改造 Dynamic Wind

**引擎 Dynamic Wind 的三个问题**（源码 `DynamicWindEval.usf`、`DynamicWindData.cpp` 已确认）：

1. **动作太少**：一个树模型只算 8 套动作，按朝向分成 8 个 45° 的桶，同一个桶里的树摆得一模一样。
2. **只有全局风**：它只接受一个全局风。
3. **姿态会跳**：摆动相位用"时间 × 风速"计算，没有状态，风速一变姿态就跳。

**做法**：在我们的插件里复制一份它的 Transform Provider 和 shader，约 1000 行，换一个新 GUID，不改引擎。

- PVE 导出的骨骼风数据 `UDynamicWindSkeletalData` 是导出类（`DYNAMICWIND_API`），原样复用。
- 和 Dynamic Wind 一样，这份代码要把 `Renderer/Private` 加进头文件路径，引擎升级时要跟着改。

**动作槽**：每个树模型 32 个共享槽，加最多 64 个专属槽。只给用到的槽派计算，全场专属槽合计不超过 256 个。

- **共享槽**：
  - 8 个朝向 × 4 种相位，按位置哈希分配，固定不变，给远处的树用。
  - 共享槽取相机处的粗风，不含近场的阵风事件，免得近处一阵风让远处所有的树一起弯。
- **专属槽**：给离相机最近的树用，每帧在那棵树的位置取近场风，按树的真实朝向计算。
- **槽的状态**：每个槽有自己的状态，相位按风速积分，风的输入做平滑（树干慢、细枝快）。风变化时姿态不跳，阵风来时有自然的滞后。
- **分配**：
  - 游戏线程给每个树模型维护一个空间索引，按距离和屏幕大小挑出最近的树。
  - 只改变化的那几棵的 `AnimationIndex`（`SetInstanceAnimationIndex`，按实例增量上传）。实例用哪个槽由 `GetSkinningDataOffset` 决定，
    它能读到这个字段。
- **交接不跳**：
  - 拿到专属槽时，从原来那个共享槽的状态起步，1 s 内过渡到本地风；
  - 释放前先过渡回去、对齐相位，再换槽。

**开销**：

- 只跟"槽数 × 骨骼数"有关，跟树的棵数无关。spike 的树有 1445 根骨骼，导出时用 PVE 的 Bone Reduction 节点减到几百根。
- 估计 10 个树模型不超过 0.2 ms，M2 实测。
- 远处很小的树用 `AnimationMinScreenSize` 停摆。

**树的资产**：

- **导出工具**：把 spike 里的导出小工具正式化，放进编辑器模块。
  - PVE 没有脚本接口，工具把导出命令排到下一帧执行，再点模态对话框里的 Export。
  - 先把叶片源网格复制到 `/Game/Weather/Trees/`，导出后保存，因为导出的资产只在内存里。
- **树种**：
  - PVE 自带山毛榉、槭、山杨、榛的样例，对得上 W7 的树种；桤木没有样例，用相近的样例改参数。
  - 每个树种 1–2 个造型，幼树和小苗先用同一模型缩小。
  - 每个造型导出有叶、无叶两份（§6.3）。
- **先验证**：M2 的第一件事是确认 PVE 的树种预设能不能生成对应的树，spike 没验证这一点。
- **不换的树**：鹅耳枥本来就是 Megascans 的普通网格（`SimpleWind` 版，不是装配体），照草的方式用材质 WPO；枯树不摆。
- **L_PyWorld（M6）**：
  - W7 的山毛榉、槭、山杨、桤木、榛从 Megaplants 静态装配体换成 PVE 树，生成节点换成 Skinned Mesh Spawner。
  - 7.4 万棵骨骼树的渲染开销是风险项。退路是远处换成同一棵树导出的静态 Nanite 版本（PVE 也能导出静态网格），PCG 按距离分两层。
  - 限制：远处的树不显示阵风事件，远处的草显示。

### 3.4 草、灌木、鹅耳枥：材质 WPO

- **现状**：
  - 草和地被用 ED 的 `M_MS_CustomFoliage`，鹅耳枥和灌木用 Megascans 的 `M_Foliage`。
  - 两个母材质都经 `MF_SimpleWind`、`MF_WindGust` 做 WPO 风：按实例根部位置弯曲，风向、风速、风力读 `MPC_GlobalFoliageActor`，
    阵风来自一张世界空间的噪声图。
- **第一步（M2，不改材质）**：每帧把相机处的风写进这个 MPC，所有草木立刻跟着我们的风向和风速走。
- **第二步**：
  - 把两个风函数里读 MPC 风的地方换成 `MF_WeatherWind`，在实例根部取风。这样背风处的草不动，阵风一道道扫过；
    原来的噪声保留，做细小的抖动。
  - `/Game/MSPresets`、`/Game/Megascans`、`/Game/Custom` 是 `ed_closure.py --copy` 复制来的，在 .gitignore 里，
    所以改动写进 `weather_foliage_materials.py`，重新复制后再跑一遍。

### 3.5 喷溅粒子和其它读风的东西

- **`NM_WeatherWind`**：
  - 用 Niagara 的 Volume Texture 数据接口直接采样近场风（它支持 `TextureRenderTargetVolume`）。
  - 粒子速度向当地风速靠拢，不同粒子的阻力不同。
  - 碰撞用场景深度或全局距离场（项目已开 `r.GenerateMeshDistanceFields`）。
- **喷溅效果**：
  - 在相机周围约 60 m 内生成：落叶（秋）、花瓣（春）、尘土（干燥大风）、吹雪（地上有雪且风速超过 8 m/s）、风暴碎屑。
  - 生成率由编排器按季节、风速和地表状态给出。§5 的雨雪粒子也用这个模块。
- **其它**：
  - 旗子和布幡：WPO 材质读 `MF_WeatherWind`，实验关卡里放一面测试旗。
  - 河面风纹：水面材质读风向和风速，M6 时接进 `M_PyWorldStream`。
  - 烟和火：Niagara 读同一个模块。
- **探针**：
  - 角色、相机、声源最多 64 个点，供 §7 使用。
  - 任意位置的查询，用每秒回读一次的地面图。

## 4. 地表天气（湿、积水、积雪、深雪、室内遮挡）

### 4.1 总体：一张地表状态图，加一个延迟 pass

- **状态**：地表状态图覆盖整个关卡，1 m 一格（L_PyWorld 是 2048²），按游戏时间每秒更新约 2 次，分块执行。
- **表现**：base pass 之后，用一个全屏 pass 按状态图改 GBuffer 里的底色、粗糙度和法线。spike 1 已验证这条路，一个材质都不用改。
  原作在 GBuffer 里多存一个湿度遮罩；我们直接改材质参数，不需要额外的通道。
- **区域性**：降水来自 Atmos，所以只有下过雨的地方才湿。从刚下过阵雨的村子走到没下雨的山坡，地面由湿变干。

### 4.2 状态怎么变（numpy 参考模型用同一套）

- **每格存**：表面湿度（0–1）、积水深度（mm）、积雪（水当量）、结冰比例。另有一张 4 m 一格的树冠与杂项状态：
  - 叶面湿度、叶上积雪：叶子比地面干得快，风一吹，叶上的雪就掉；
  - 雪龄：新雪亮，旧雪发灰；
  - 落叶量（§6.3）。
- **输入**：
  - Atmos 地面图：降水率、雨雪比例、近地面气温、湿度、云量（换算成日照）；
  - 近地面风；
  - 烘焙数据：遮挡、地表类型、积水潜力。
- **气温**：Atmos 一格 62.5 m，按 6.5 °C/km 换算到每个 1 m 格子的真实高度。雪线因此自然出现：谷底下雨，山脊积雪。
- **下雨**：
  - 先润湿表面，约 0.5 mm 雨水就全湿；中雨 5 mm/h 时约 6 分钟（游戏时间）。
  - 多出来的水按积水潜力汇成积水：路面、广场、低洼处先积，坡面和草地不积。
  - 一部分下渗。
- **变干**：
  - 蒸发速率由气温、湿度、风速、日照决定。晴天 20 °C、有微风时，表面 1–2 个游戏小时干透；阴天无风时慢得多。
  - 积水从边缘慢慢缩小，浅的几小时就消失，深的可能留到第二天，所以会出现"路面已干、坑里还有水"。
- **下雪**：
  - 气温 ≤ 约 0.5 °C 才积；否则落地即化，只让地面变湿。
  - 风会搬雪：用实体高度沿风向算遮蔽度（Winstral 的方法），墙后和房子背风侧堆得厚，迎风的高处被吹薄。
  - 树冠截留一部分雪。
- **融雪**：
  - 由气温（度日法）、日照（按云量和雪的反照率）和落在雪上的雨共同决定。
  - 化出来的水依次变成湿面、积水，再蒸发或下渗。原作"雪 → 湿 → 积水 → 干"的顺序在这里是算出来的。
- **结冰**：雨后气温降到 0 °C 以下，积水和湿面慢慢结冰；回暖再化。
- **编排和手动覆盖**：编排器可以调各项速率、锁定状态；手动覆盖直接写这张图，比如"全图积雪 30 cm"、"全干"。
- **初始状态**：直接进入某个季节时（新开局，或调试、剧情直接指定季节），按该季节的气候给起始值，比如冬天先铺一层雪。
  正常换季过渡时不预铺，由物理过程自然积累，避免画面突变（§6.5）。

### 4.3 室内和屋檐遮挡

- **状态图管哪一层**：状态图每格只代表最上面那层表面，比如屋顶、桥面或开阔地面。
- **被盖住的表面**：屋里、檐下、桥下，在延迟 pass 里逐像素判断。
  - **判断方法**：在烘焙的实体高度上，沿雨落下的方向做一次 3–4 次采样的高度场光线步进；被挡住就算遮蔽，不湿、不积雪、没有积水。
  - **斜雨**：风大时雨是斜的，步进方向也跟着斜。迎风的墙面和窗边会湿，雨能飘进窗口一段；背风面和檐下保持干燥。
    这和原作"屋檐下没有雨，但雨能从窗口飘进室内"一致。
  - **雪**：雪下得慢、被吹得更斜，所以飘得更远。
  - **树冠**：不算实体。树下的格子按冠层疏密少接一些雨雪，也干得更慢。
- **和原作的区别**：原作的室内体积要人工摆平面，我们直接用烘焙的几何高度。代价是 2.5D：同一列只有最高那一层算露天。
- **其它用途**：这份遮挡还用于 §5 的中远距离雨雪粒子剔除、§5.5 闪光的室内遮挡，以及 §7 的角色淋雨和声音的室内外判断。

### 4.4 延迟 pass：怎么改 GBuffer

**挂接位置**：`FSceneViewExtensionBase::PostRenderBasePassDeferred_RenderThread`，只在视图矩形内绘制。项目开着 Substrate 的 blendable
GBuffer（`r.Substrate.ProjectGBufferFormat=0`），base pass 输出传统 GBuffer 布局。

**读取**（已在 5.8 shader 源码里确认）：

| 来源 | 内容 |
|---|---|
| 深度 | — |
| GBufferA | 法线，线性编码 N × 0.5 + 0.5，可以直接混合 |
| GBufferB | 金属度、高光、粗糙度、着色模型 |
| GBufferC | 底色和材质 AO。项目 `r.AllowStaticLighting=False`，C.a 就是材质 AO |
| GBufferD | 自定义数据，双面植被的透光色在这里 |

**湿**（Lagarde 的 Water drop 模型）：

- 多孔程度按粗糙度和金属度估计。粗糙的土、石、混凝土变暗多；金属和光滑面不变暗，只是变得更亮滑。
- 粗糙度朝水膜的值降低。植被叶子变得更亮滑、略暗。

**积水**：

- **形状**：积水深度 × 积水潜力 + 世界空间噪声，边缘有一圈湿带。
- **水里**：底色压暗，粗糙度约 0.02，法线拉平朝上，再叠两层：
  - 雨点涟漪：Python 预生成的法线序列图，密度随雨强变化；
  - 风纹：方向和强度来自 §3 的风。
- **出现位置**：只在平的、露天的、非植被的表面上。
- **结冰后**：没有涟漪，粗糙度略升，带一点白。

**雪**：

- **覆盖度**：积雪深度 × 朝上程度（法线阈值，竖直面不积）× 微遮蔽（材质 AO，缝隙里雪少）× 噪声（薄雪是斑驳的）。
- **外观**：底色变成雪色（新雪约 0.9，越旧越灰），粗糙度约 0.7，法线随厚度向上抹平细节。
- **植被**：GBufferD 里的透光色按积雪减弱，对应原作"雪越多，植被透光越低"。
- **落叶层**：秋天按落叶量把冠层下的地面染成落叶色（§6.3）。

**排除角色**：

- 角色网格写 Custom Stencil，延迟 pass 跳过这些像素。
- 项目设置里把 Custom Depth-Stencil 设成带 stencil 的模式。`r.CustomDepth.Order` 设成 0，保证它在 base pass 之前画好；
  5.8 在开 DBuffer 时默认也是这样。
- 角色自己的湿身和落雪见 §7。

**已知限制和对策**：

- Lumen 的表面缓存和离屏反射里，物体看不到湿和雪（spike 已确认，Anvil 也一样）。
- 地面面积大，冬天它对反弹光影响明显，所以地形材质自己也画雪，用同一个材质函数 `MF_WeatherSurface`。这样 Lumen 的漫反射和反射里，
  地面也是白的。
- 延迟 pass 跳过地形，避免把雪画两次。用 stencil 的哪一位标记地形，M1 再定。

**开销**：目标 ≤ 0.3 ms（1440p 内部分辨率）。

### 4.5 深雪变形

- **做法**：地形材质开 Nanite tessellation，Displacement = 积雪深度（状态图）− 压痕（变形图）。整片地形都被雪抬高，远近一致，没有接缝。
  - **前提**：L_PyWorld 的运行时地形现在是 Nanite 静态网格（MPD 构建变体已修好，traps 128–131），但还没在上面验证过
    "地形材质 + tessellation"。
  - **验证和退路**：M4 先做这个小验证。行不通就退回 spike 4 验证过的做法——Nanite 网格加运行时渲染目标驱动的 tessellation——
    做成相机周围一块贴地的可变形雪面。
  - **查看方式**：编辑器视口里的 MeshTerrain 是预览代理，看不到深雪，要进 PIE 或 Simulate 看。
- **压痕**：
  - **范围**：变形图覆盖相机周围约 50 m，5 cm 一像素（1024²），跟着相机滚动。
  - **压印器**：数据驱动，和原作一样能压胶囊或贴图。来源有角色的脚（按骨骼高度判断落地）、马蹄、身体倒地、拖痕。
    组件挂在角色上，接线见 §7。
  - **随时间变化**：新雪按降雪速率慢慢把压痕填平；融雪时雪变薄，压痕也跟着变浅。
  - **移出窗口**：区域移出窗口时，把压痕的平均值写回 1 m 状态图（减少那里的积雪）。所以踩出来的小路回头还在，只是没有脚印细节。
- **法线**：材质按变形图的梯度算，脚印边缘的光照是对的。
- **碰撞**：碰撞仍是地面，所以人和马会陷进雪里，视觉上正好对。深雪减速属于玩法，不做。
- **开销目标**：压痕更新 ≤ 0.05 ms，tessellation 的额外开销 ≤ 0.3 ms，M4 实测。

### 4.6 烘焙（`weather.py bake`）

**每关生成**：

- **Atmos 用（62.5 m）**：地形、水体、植被覆盖。
- **其余部件用（1 m）**：

| 图 | 用途 |
|---|---|
| 地形高度 | 近场风贴地、深雪 |
| 实体高度 | 风的障碍物、遮挡判断 |
| 冠层顶高和疏密 | 风的阻力、截留雨雪 |
| 地表类型（土、草、路、石板/广场、屋顶、水） | 下渗、积水潜力、脚步声 |
| 积水潜力 | 实体高度的局部凹陷 × 平坦程度 × 地表类型 |
| 水面高度 | 角色蹚水（§7） |
| 美术遮罩（可选） | 对应原作技术美术画的冷区和暖区，在物理结果上再乘一层（比如温泉边不积雪、某处永远湿） |

**生成方式**：

- 用按组件分类的俯视深度捕获，加上关卡数据栅格化。
- L_PyWorld 的分类来源：W1 地形，W3 河，W4 路，W5 桥，W6 房子和广场，W7 乔木、灌木、岩石，W9 地表材质。
- 实验关卡按标签分类。

**存放和版本管理**：

- 结果放在 `/Game/Weather/Bake/<关卡>/`，同时保存一份 CPU 可读的实体高度。
- L_PyWorld 的烘焙结果和它的生成内容一样不进 git：打开关卡、生成完 W1–W9 后再跑 bake。
- 实验关卡的烘焙结果小，进 git。

### 4.7 验收（M1 地表 + M4 深雪）

| 场景 | 预期 |
|---|---|
| 中雨（5 mm/h），从干开始 | 开阔地面约 6 分钟（游戏时间）全湿；屋里、檐下、桥下保持干；Lumen 反射里湿面有反光 |
| 斜风雨（风速 8 m/s） | 迎风墙面和窗边变湿，背风面和檐下是干的 |

| 雨停，晴天 20 °C、微风 | 表面 1–2 个游戏小时干透；积水从边缘缩小，几小时后消失；阴天无风时明显更慢 |
| 降雪（−3 °C） | 朝上的面先变白，竖直面不积，缝隙里雪少；植被透光随积雪下降；角色不受影响 |

| 水量守恒（numpy） | 降水 = 存量变化 + 蒸发 + 下渗，误差 < 0.5%；GPU 与 numpy 一致 |

| 性能 | 延迟 pass ≤ 0.3 ms，状态更新 ≤ 0.05 ms，深雪 ≤ 0.35 ms |

## 5. 云与降水（云、雨雪、雷暴、雾）

### 5.1 一份模拟数据，从天上到地面

云、远处的雨幕、近处的雨雪粒子、地面变湿，全都来自 Atmos。远处看到那片云在下雨，走过去那里真的在下；走出雨区，雨就停了，地面慢慢变干。

### 5.2 体积云

- **载体**：UE 的 Volumetric Cloud，换上我们的云材质 `M_WeatherCloud`。spike 3 已验证它能每帧采样 compute 写入的体积纹理
  （采样器类型用 Color，写完调用 `UseExternalAccessMode(SRV)`）。云层底部设在地面，高 8 km，与 Atmos 一致。
- **形状分两级**：
  - **宏观**：Atmos 的云水决定云在哪、云底和云顶有多高。
  - **细节**：3D 噪声侵蚀边缘，噪声用 Perlin-Worley 加 Worley，在插件启动时用 compute 生成一次。噪声按低、中、高三层，
    分别随各层 Atmos 的风平移，细节跟着云走。
  - **云型由模拟量决定**：
    - 上升气流强的地方是积云：云底平，顶部像菜花，噪声侵蚀偏向下部；
    - 上升弱的地方是层云：表面平滑，边缘呈丝缕状；
    - 高处冰多的地方是砧状云和卷云：纤维状。
- **雨幕**：云底以下按降水量加一点消光，雪幕偏白。远处的阵雨因此是一道道看得见的灰色雨幕。
- **远景（模拟区域外）**：
  - **为什么要远景**：模拟只覆盖 8 × 8 km，但站在山脊上看到的天空大部分在几十公里外。
  - **远景天气图**：区域外用远景天气图补上，覆盖约 128 × 128 km，每秒更新。覆盖率、云型、降水由天气型决定，图案随大尺度的风移动。
  - **衔接**：靠近区域边缘的部分，由模拟每一柱的统计量生成，衔接处没有缝。
  - **天气型切换**：以锋面的形式从上风方向扫过来。远景图里先看到云带靠近，然后模拟区域的来流边界才变。
    §2.2 的 1–3 小时过渡，就是这条锋面带经过所需的时间。
- **光照**：
  - **云影**：方向光开 `bCastCloudShadows`，云影在地上移动，方向和太阳一致。§4 计算蒸发和融雪用的日照来自同一份云量。
  - **天光**：用实时捕获，所以阴天和暴风雨时环境光自然变暗、变冷，Lumen 也跟着变。
  - **近地的雾**：贴地约 150 m 以内的雾不在云里画，交给 §5.3。再往上的低云照常画，相机进到山顶的云里也能看到。
- **开销**：云不计入天气预算，单独目标 ≤ 2.5 ms（1440p），M3 实测。

### 5.3 雾

- **高度雾**：只保留一个，开体积雾。密度和高度衰减由三样东西决定：相机处的 Atmos 雾量、降水（雨雪降低能见度）、湿度。
  它的第二层用来做谷底的低雾。
- **局部雾体积**（5.8 的 Local Fog Volume）：在 Atmos 雾量高的格子上放一组，最多约 16 个，每个几百米大小，淡入淡出。
  效果是清晨山谷里一团团的雾，从山上看得见，太阳出来后散去。

### 5.4 近处的雨和雪

- **Niagara 系统**：挂在相机上，在周围约 30 m 内生成粒子。
  - **雨**：
    - 雨丝顺着速度方向拉长。
    - 雨越大，大雨滴越多（按 Marshall-Palmer 分布），雨丝就越长、越粗。
    - 下落速度按雨滴大小取 2–9 m/s。逆光时有亮闪。
  - **雪**：雪花约 1 m/s 下落，带翻转和飘动；暴风雪时几乎横飞。
  - **雨夹雪**：按雨雪比例混合两种粒子。
  - **输入**：
    - 风来自 `NM_WeatherWind`；
    - 降水率和雨雪比例来自地面图。M1 时还没有 Atmos，由手动覆盖给出。
- **遮挡**（对应原作的"定向深度图"）：
  - **定向深度捕获**：沿雨落下的方向，对相机周围约 40 m 做一张正交深度捕获（512²）。雨的方向变化或相机移动时更新，约每秒 4 次。
  - **效果**：粒子落到被挡住的位置就消失，并在那个表面溅起水花。所以屋檐下没有雨，雨能从窗口飘进去一段，屋顶上有溅落。
  - **40 m 以外**：改用 §4.3 的高度场遮挡判断。
- **中远距离**：
  - **雨层**：在相机外套 2–3 层圆柱面（约 8、20、50 m），贴上滚动的雨丝或雪花贴图。方向按"下落 + 风"在屏幕上的投影，
    并按场景深度淡出。
  - **更远**：再往外是雾，以及云里的雨幕。
  - **效果**：大雨从近到远都有层次。
- **溅落**：
  - 20 m 内落地的雨点溅起小水花。
  - 积水里的涟漪在 §4.4。
  - 河面的雨点涟漪由水面材质读降水率生成（M6）。
- **贴图**：雨丝、雪花、溅落序列先用 Python 生成简单版本，以后可以换成美术资源。

### 5.5 雷暴和闪电

- **来源**：Atmos 的雷暴潜势。发生频率按潜势的总量，位置按潜势的分布随机抽取。云内闪（只照亮云）与云地闪约 3 : 1。
- **云地闪**：
  - **形态**：从当地的云底劈到地面，用 Niagara ribbon 程序生成，带分叉。持续 0.2–0.6 s，闪 2–4 次（回击）。
  - **落点**：在抽到的位置附近约 50 m 内，做竖直射线检测，挑最高的物体。所以树和钟楼更容易被劈。
- **闪光**：
  - **云**：云材质按闪电位置加一团自发光，云从里面被照亮。云内闪也这样画。
  - **地面**：
    - 一盏朝向闪电的不投影方向光短暂点亮，同时天光强度短暂提高。
    - 这盏光的光照函数读 §4.3 的遮挡，所以屋里和檐下不会被直接照亮。
    - 不投影是为了省掉闪光那几帧的阴影开销，代价是闪电没有影子。
- **雷声**：按"距离 ÷ 343 m/s"延迟（§7.5）。
- **阵风锋**：雷暴的下沉气流同时交给 §3，产生阵风锋。

### 5.6 资产和关卡

- **资产位置**：云材质、降水和闪电的 Niagara 系统、雨层材质和生成的贴图放在插件的 `Content/` 里（§1.6）。
- **L_PyWorld 的天空**：L_PyWorld 现在有两个 Volumetric Cloud（City Sample 的 `MI_VolumetricCloud_01` 和 `_Vancouver`）、
  两个天光、两个高度雾，看起来是复制模板时留下的。M6 时收成一套，由天气系统驱动。

| 阴天 | 整片层云，地面变暗，环境光变冷、变暗 |
| 锋面过境 | 远景里云带从上风方向靠近，进入模拟区域后开始下雨；整个过渡 1–3 游戏小时 |
| 一致性 | 远处云下的雨幕，走过去时那里真的在下雨（有粒子、地面变湿）；走出雨区，雨就停了 |
| 雷暴 | 积雨云顶部是冰相的砧状；闪电多落在高处；雷声的延迟随距离变化；闪光时屋里不被照亮 |
| 雾 | 清晨山谷里有雾（Atmos 算出），太阳出来后散去；雨雪天能见度下降 |
| 性能 | 雨天合计 ≤ 1.9 ms，雪天 ≤ 2.05 ms（§1.7），云 ≤ 2.5 ms |

## 6. 四季（昼夜、气候、植被、多状态物体）

### 6.1 日历和时钟

- **游戏时间**：日期加一天中的时刻，流速是参数（默认 1 游戏日 = 1 真实小时）。调试时可以暂停、快进、跳到任意日期。
- **季节**：
  - 离散的四个值，默认每季 7 个游戏日。
  - 季节内日期照常往前走，每个游戏日日期前进约 13 天，所以一季之内太阳轨迹也是平滑变化的。
  - 剧情或调试可以直接指定季节，也可以锁定。
- **太阳**：
  - 位置用 NOAA 算法自己算（几十行，C++ 和 numpy 各一份，可以离线对照），不依赖 SunPosition 插件。
  - 纬度默认 35°N：夏至正午太阳高 78°、昼长约 14.4 h；冬至 32°、约 9.7 h。季节之间的日照差别自然就出来了。
- **月亮和星空**：
  - 月亮是第二盏方向光（大气光源 1），亮度按月相（29.5 天一个周期）和高度决定。
  - 夜里有一个星空球（星图由 Python 生成）淡入，云挡在它前面。
- **曝光和调色**：自动曝光的范围要覆盖白天到月夜。调色预设按"季节 × 时刻 × 天气"组合，由编排器混合，对应原作氛围图管调色和后期的部分。

### 6.2 气候

- **气候表**：每关一份（`DA_Climate`），按季节给出：
  - 气温的日均值和日较差，以及湿度；
  - 天气型的出现概率和持续时间，写成一个转移矩阵，编排器从这里抽天气型序列；
  - 盛行风的方向和风力；
  - 起雾和雷暴的概率与时段，比如夏天午后多雷暴、秋冬清晨多雾。
- **随机种子**：天气型序列用带种子的随机数生成，种子存进存档。同一个种子得到同一串天气，便于复现和测试。
- **对 Atmos 的影响**：季节改变 Atmos 的来流廓线（§2.2）；地表积雪反过来影响 Atmos 的地面加热（§2.4）。

### 6.3 植被的四季外观

**现有机制**（已在资产里确认）：

- Megascans、ED 的草木，以及 PVE 树的叶片母材质，都带同一套 `MF_HealthSeason`。
- 它读 `MPC_GlobalFoliageActor` 里的 Season Strength、Brightness、Saturation 和 Health；每个材质实例再自己定季节叠加色、强度和偏移，
  逐顶点还有变化。
- PVE 的 `MA_Foliage_Trees` 用的是它自己那份 MPC，所以季节参数两个 MPC 都要写。

**驱动方式**：

- `MPC_Weather` 存四个季节的混合权重，过渡时交叉淡入淡出，再换算后写进上面两个 MPC。
- 季节变化走材质，所以 Lumen 的反弹光和反射里也是对的。这点和 §4 的延迟天气不同。

| 植被 | 春 | 夏 | 秋 | 冬 |
|---|---|---|---|---|
| PVE 树（山毛榉、槭、山杨、桤木、榛） | 嫩绿 | 深绿 | 各树种的秋色：山毛榉铜褐、槭橙黄、山杨金黄、榛黄；桤木落叶时还偏绿 | 换无叶网格（spike 已验证），枝上积雪由 §4 画 |
| 鹅耳枥（Megascans） | 嫩绿 | 深绿 | 黄 | 留着褐色枯叶（鹅耳枥和山毛榉的幼树冬天常这样），不换网格 |
| 接骨木（灌木） | 嫩绿 | 绿 | 黄褐 | 没有无叶资产：按比例隐去大部分，剩下的变褐、盖雪 |
| 草 | 嫩绿 | 绿 | 金黄（原作的"金色草地"） | 枯黄，被雪盖住 |
| W7 里 8 种开花的地被 | 银莲花、铃兰、长春花开 | 夏天开花的那几种 | 很少 | 没有 |
| 地形的草地层 | 嫩绿 | 绿 | 金黄 | 枯黄 |
| 树下的落叶 | — | — | 落叶期冠层下越积越厚（地表的落叶量通道，§4.2） | 被雪盖住，化雪后露出来 |

- **物候错开**：
  - 每株植物的早晚写进实例自定义数据，值 = 高度 + 随机。秋色从山上往下走，春绿从山下往上走，入秋时不会所有树一起变色。
  - PCG 的 `UPCGInstanceDataPackerByAttribute` 能把点属性打包进实例数据，静态网格和骨骼网格各有一个版本。
  - W7 现在没写这类数据，M6 时加上。
- **隐去和显示**：地被花、冬天的灌木，由材质按季节和实例自定义数据用 WPO 把顶点缩到 0，不用重跑 PCG（W7 重跑一次要 118 s）。
- **改材质**：
  - ED 和 MSPresets 的母材质改动并进 `weather_foliage_materials.py`。
  - PVE 树的叶片材质在导出时复制到 `/Game/Weather/Trees/`，按树种做好秋色的材质实例。
- **春天的开花树**（原作的樱花）：PVE 没有开花的样例，项目里也没有花簇资产。v1 用嫩绿加地被花表现春天。
  开花树作为可选项：要做就用 PVE 做一种，花簇网格先程序生成。
- **可选，v1 不做**：PVE 有针叶树样例，可以在高处加一种常绿树，让冬天山上还有绿色。这要改 W7 的物种表。

### 6.4 多状态物体

- **机制**：
  - 用 `UWeatherVariantComponent` 加 `DA_WeatherVariant`，列出每个状态下的网格、材质、显隐、特效和碰撞。
  - 切换条件可以是季节、昼夜，也可以是地表状态，比如连续冰冻的天数、屋顶有没有雪。
  - PCG 生成的内容，在生成时打上季节标签，按标签切换组件。
- **为什么用组件级显隐**：L_PyWorld 是 World Partition 关卡，运行时 Data Layer 也能做季节切换，但 PCG 生成的组件不好分层。
- **v1 的物体**：
  - **池塘和水洼**：
    - 连续几天日均气温低于 0 °C 才冻上，换成能站上去的冰面，对应原作冬天不能潜水躲藏。回暖后化开。
    - L_PyWorld 只有河：河不冻，只在岸边结一圈薄冰（材质）。冰面在实验关卡的池塘上验证。
  - **屋檐冰柱**：
    - 屋顶有雪、白天化夜里冻时，沿屋檐长出来。
    - 没有冰柱资产，用 Geometry Script 程序生成；W6 知道每栋房子的屋檐线。
  - **农田和菜园（W6）**：
    - 春天出苗，夏天茂盛，秋天金黄、收割后留茬，冬天裸土或盖雪。
    - 作物先用现有的草类网格着色代替。
  - **昼夜**（同一套机制）：
    - W8 的路灯天黑亮、天亮灭。
    - 窗户夜里亮灯：给 `pyworld_town_materials.py` 生成的窗户材质加夜间自发光。

### 6.5 换季过渡

编排器的季节状态机：四个季节状态，加四个过渡状态。过渡期默认 1 个游戏日（参数），按以下顺序进行：

1. **切换气候**：气候表切到下一季。比如秋入冬时，第一场寒潮和初雪变得很可能出现；雪由物理过程自然积起来，不预铺（§4.2）。
2. **材质渐变**：材质的季节权重在过渡期内渐变，每株植物按自己的物候早晚错开。
3. **秋入冬**：
   - 落叶粒子（§3.5）大量出现，树下的落叶层变厚。
   - 树换成无叶网格。只换视野外的组件，每帧最多一个，每个 0.2–0.4 ms。视野里的组件，等玩家转身、天黑或大雪大雾时再换。
4. **冬入春**：
   - 雪按 §4 的物理过程慢慢化。
   - 无叶网格换回有叶，同样只在视野外换。
   - 地被花长出来。
5. **多状态物体**：按各自的条件切换，也只在视野外切。
6. **调色**：调色预设交叉淡化。

**内存**：冬季网格在秋天提前异步加载，夏天卸载，其余时间不占内存。

### 6.6 验收（M0 时钟、M3 气候、M4 季节）

| 场景 | 预期 |
|---|---|
| 太阳位置（M0） | 与 NOAA 参考值相差 < 0.1°；35°N 夏至昼长约 14.4 h，冬至约 9.7 h |
| 月亮（M0） | 29.5 天一个周期；满月夜明显比新月夜亮 |
| 气候统计（M3） | 离线只跑天气型序列 100 年：各季节各天气型的出现频率与气候表相差 < 5%；同一种子得到同一串天气 |
| 四季外观（M4） | 实验关卡同一机位、同一时刻的四张截图：春天嫩绿加地被花；夏天深绿；秋天各树种秋色、金色草地、树下落叶；冬天无叶、积雪、冰柱、冰面 |

## 7. 角色与声音

### 7.1 前提：MetaHuman 由用户生成

- **为什么要用户来做**：
  - 引擎的 MetaHuman Creator（MetaHumanCharacter 插件）只带头发材质，没有任何发型（groom）资产。
  - 自动绑定和高清贴图都是云服务请求。
- **需要做什么**：用户在编辑器里登录 Epic 账号，用 MetaHuman Creator 生成测试角色，下载一套发型和衣服。M5 开始前做一次即可，
  之后接天气由我们完成。
- **退路**：没有 MetaHuman 时，湿身和落雪在模板的 Manny/Quinn 上验证；头发和衣服随风等有了 MetaHuman 再接。
- **范围**：只做角色的外观和物理。NPC 的感知和反应不做（§0.2）。

### 7.2 角色的天气状态（`UWeatherCharacterComponent`，CPU 约 10 Hz）

- **输入**：
  - 角色所在处的降水、气温、湿度、日照：地面图的 CPU 副本；
  - 头顶有没有遮挡：烘焙实体高度的 CPU 副本，沿雨落下的方向做 §4.3 的判断；
  - 风：角色身上的探针；
  - 水：烘焙的水面高度图，角色站在河里时知道水面有多高；
  - 脚下：玩家周围 32 × 32 m 的地表状态，包括积水、积雪深度、湿度、冰和落叶。
- **状态**：
  - **雨湿**：露天淋雨时从头肩往下湿，几分钟（游戏时间）湿透。干得快慢取决于气温、湿度、风和日照：屋里慢，晴天有风快。
  - **湿线**：蹚水时水面以下立刻湿透；跑过积水，湿线升到小腿。
  - **身上的雪**：雪天在露天时，雪积在朝上的部位（头顶、肩、手臂），跑跳会抖掉一部分。气温高于 0 °C 或进屋就化，变成湿。
  - **雪线**：走过深雪，小腿沾上雪，高度等于雪深。
- **计算**：与 §4.2 用同一套蒸发、融化公式；numpy 参考模型也实现。

### 7.3 角色身上怎么画湿和雪

- **原作做法**：原作角色湿身走角色自己的图层系统，不走地表的延迟 pass；§4.4 已用 Custom Stencil 把角色排除在外。
- **叠加材质**：
  - 给身体和衣服挂一个叠加材质（Overlay Material，5.8 还支持按材质槽单独设）`M_WeatherCharacterOverlay`，
    状态量用 Custom Primitive Data 传进去。
  - 不改 MetaHuman 和 Manny 的材质：MetaHuman 的母材质在引擎插件里，重新组装角色时材质还会重建。
- **湿**：
  - 叠一层带光照的半透明薄层，颜色偏暗、粗糙度很低：衣服看起来变深，皮肤发亮。
  - 下雨时叠流动的水珠法线。湿线处边缘做柔和过渡。
- **雪**：朝上的面按积雪量和噪声画成白色；雪线以下的小腿也画白。
- **代价**：每个角色多画一遍半透明，只给近处的角色开（叠加材质可以设最大绘制距离）。
- **头发**：发丝不支持叠加材质，用它材质已有的参数表现湿（颜色更深、更亮）。头发上的雪 v1 不做。
- **雨打在身上**：近处主角的头肩上有小水花，由 Niagara 从网格表面朝上的地方发射。
- **可选**：气温不高于 5 °C 时，角色呵出白气。

### 7.4 风吹衣服和头发

- **衣服（Chaos Cloth）**：
  - 每帧把角色探针的风（含阵风）通过 `UChaosClothingSimulationInteractor::SetWind` 交给布料。
  - 衣服湿了以后，阻力和升力变小、阻尼变大，衣服飘得少、更贴身。
- **头发（Groom）**：
  - groom 资产允许指定自定义解算器（`CustomSolver` + `CustomSystem`）。复制一份引擎的发丝解算器，加一个读取近场风体纹理的模块，
    每根发丝按自己所在位置的风受力：背风处不动，阵风来时一起扬起；头发湿了以后更重。
  - 5.8 的发丝除了 Niagara 解算器，还有基于 Deformer Graph 的解算器。M5 先确认 MetaHuman 发型用的是哪种，两种都能读体积纹理。
- **深雪压印器**：§4.5 的压印器在这里接到角色的脚上，按脚骨骼的高度判断落地。

### 7.5 声音

**现有素材**：`Content/Audio` 是 City Sample 的音频库，共 1496 个资产，在 .gitignore 里。

- 有：风声循环，比如 `sfx_amb_Pawn_Wind_lp_meta`、`sfx_Wind_High_Cold_Blustery_lp_01`；几种鞋踩水泥地和踩积水的脚步声。
- 没有：雨、雷、雪的声音；草地、泥土、落叶上的脚步声；鸟叫和虫鸣。

**缺的先用 MetaSounds 合成**，以后拿到录音素材再替换或叠加。

- **雨**：
  - 滤波噪声打底，叠上随机的雨点声。
  - 雨点的音色按落点区分：树叶清脆、屋顶咚咚、水面叮咚、地面发闷。
  - 密度和音量跟着雨强变。
- **风**：
  - 用现有的风声循环，音量、滤波和音高跟着探针的风速和阵风变化。
  - 靠近墙角、屋檐，近场风有局部加速时，加一层呼啸（带通噪声）。
  - 周围树多时加树叶的沙沙声，强度按烘焙冠层 × 风速。
- **雷**：
  - 闪电每一段到听者的距离不同，按各自的距离延迟（÷ 343 m/s）后叠加，方法取自 Andy Farnell 的合成方法。
  - 近处是一声炸响，远处是滚雷，雷声的长短和闪电的形状对得上。
  - 高频随距离衰减得更快。
- **脚步**：
  - 声音由地表类型和地表状态共同决定。
    - 地表类型来自烘焙。石板和路面用现有的水泥地脚步声，另有土、草、木桥。
    - 地表状态：湿地加一层"吧唧"声；积水用现有的踩水声；雪按深度合成咯吱声；冰和落叶另外合成。
  - 触发时机和深雪压印器共用同一个"脚落地"判断。
- **季节环境声**：蝉和蟋蟀可以合成；鸟叫需要录音素材，v1 只留接口。

**空间感和室内外**：

- **底层声和点声源**：
  - 听者周围有几条循环的底层声：雨、风、树叶。
  - 另有最多 8 个点声源：在 25 m 内的屋顶、树冠、水面上放"雨打在这里"的声音。人走动时，雨声的方向和质感跟着变。
- **封闭程度**：在听者头顶做 §4.3 的遮挡判断，再看周围 5 m 一圈有多大比例被盖住，得到"封闭程度"。
- **屋里的效果**：外面的声音变闷、变小，屋顶的雨变成头顶的鼓点声，混响换成室内的。这对应原作"室内体积也用于声音"，但不用人工摆体积。
- **统一调节**：这些量用 Audio Modulation 的控制总线统一调，City Sample 的音频本来就是这样组织的。

### 7.6 验收（M5，在实验关卡）

| 场景 | 预期 |
|---|---|
| 淋雨 | 头肩先湿，几分钟（游戏时间）湿透：衣服变深、皮肤发亮、有水珠；躲到檐下就不再变湿，慢慢变干（晴天有风快，阴冷慢） |
| 蹚水、跑过积水 | 进河后水面以下立刻湿透；跑过积水，小腿溅湿 |
| 落雪 | 头顶和肩上积雪，跑跳会抖掉一部分；进屋化成湿；走过深雪，小腿沾雪 |
| 风吹衣服、头发 | 顺着本地风飘；走到房子背风处明显变弱；阵风来时一起扬起；湿了以后飘得少 |
| 和地表互不干扰 | 角色只显示自己的湿和雪，不会被地面的延迟 pass 再画一遍 |
| 雨声 | 随雨强变化；树下、檐下、屋里、水边听起来不一样（屋里是头顶的鼓点，外面变闷） |
| 风声 | 随风速和阵风起落；靠近墙角、屋檐时有呼啸 |
| 雷声 | 延迟和距离对得上（约 3 s ≈ 1 km）；近处炸雷，远处滚雷 |
| 脚步声 | 随地面变化：干石板、湿石板、积水、雪、落叶 |
| 性能 | 每个角色的天气状态 ≤ 0.05 ms（CPU）；每个近处角色的叠加材质 ≤ 0.1 ms（GPU）；同时发声 ≤ 20 个 |

## 8. 测试

### 8.1 四层

| 层 | 测什么 | 怎么跑 | 什么时候跑 |
|---|---|---|---|
| 离线参考模型 | 物理和逻辑本身对不对 | numpy，`Tools/weather/tests`，pytest | 每次改动后 |
| C++ 自动化 | GPU 结果是否和参考模型一致；CPU 逻辑 | `SeasonalWeather.*` 自动化测试，离屏渲染 | 提交前 |
| 场景测试 | 整套系统在关卡里的表现 | 在 `L_WeatherLab` 里经 MCP 桥跑 `weather.py scenario` | 提交前跑冒烟集，里程碑结束跑全部 |
| 人工评审 | 好不好看、好不好听、像不像原作 | 截图集、录音、原作对照表 | 每个里程碑结束 |

性能、长时间运行和存档是贯穿这四层的专项（§8.5、§8.6）。

### 8.2 离线参考模型（numpy）

- **覆盖范围**：
  - **Atmos**：
    - 单项物理：饱和、凝结放热、Kessler 转化、浮力、平流守恒、投影后的散度；
    - 场景：§2.7 的各个场景；
    - 水量守恒。
  - **近场风**：均匀来流、坡面无假风、房后背风、林缘、阵风到达时间、窗口平移。
  - **地表状态**：水量平衡；变湿和变干的时间；积水只出现在该出现的地方；积雪、融化、再冻；背风堆雪；落叶层。
  - **角色状态**：淋湿和变干；湿线；雪积上去和抖掉；雪化成湿。
  - **日历、太阳、月亮**：与 NOAA 参考值对照，检查昼长和月相；气候统计（天气型序列跑 100 年）；同一种子得到同一串天气。
  - **烘焙后处理**：积水潜力、背风遮蔽度，用合成的小高度图测。
  - **树的专属槽交接**：相位对齐的计算，保证姿态连续。
  - **声音参数映射**：从天气输入算 MetaSounds 参数的纯函数。
- **和 GPU 用同一套算法**：插值方式、多重网格的迭代安排都相同，所以能逐步对照，不只是统计上接近。
- **参数一致性**：参数 JSON 和 C++ 共用，有一个结构校验测试保证两边读的键一样。

### 8.3 GPU 对照与 C++ 自动化

- **输入和基准**：
  - 标准场景由 Python 生成：平地、30° 坡、山脊、山谷、单栋房子、林缘。
  - numpy 算出的基准结果存成小文件，放在 `Tools/weather/golden/`。网格都很小，进 git。
- **比对**：自动化测试在 GPU 上跑同样的输入，回读后比对。
  - 单步：相对误差 < 1e-3，主要受 fp16 存储精度限制。
  - 多步：湍流会发散，所以比较时间平均后的场，误差 < 5%。
- **可重复**：GPU 代码里不用浮点原子加，同一台机器上每次结果都一样，基准数据和基准截图才靠得住。
- **命令**：
  - 和 PyPCGTools 的自动化测试一样，但要用 GPU：把 `-nullrhi` 换成 `-RenderOffscreen`。
  - 跑之前两个编辑器都要关掉。
  - M0 先验证这条命令能在离屏状态下跑 GPU pass。
- **纯 CPU 逻辑**：日历、季节状态机的切换、树的专属槽分配、多状态物体的切换条件、存档的序列化。

### 8.4 场景测试（`L_WeatherLab`）

- **实验关卡**：
  - 由 `weather_lab.py` 生成，约 300 × 300 m，正好罩住 256 m 的近场窗口。
  - 内容：开阔草地、30° 坡、带屋檐和门窗的房子（能进屋）、一段墙、跨小溪的桥、池塘、路面和广场、留脚印用的土路、
    一片 PVE 树林和林缘、一面旗、一盏路灯、角色出生点。
  - 每个验收项有固定的机位。
  - Atmos 的越山、日变化场景不用这个关卡（它太小，撑不起 8 km 的模拟），改用合成的地形烘焙。
- **运行器**：`weather.py scenario {"name": ...}`。
  - 先设手动覆盖或强制天气，再冻结或加速时间，然后运行，记录指标和截图。
  - 结果写进 `Saved/Reports/weather/<name>.json`，截图放在同一目录。
  - 长时间运行用 `{"defer": true}`，因为长的桥调用会丢回复，和 PyPCG 城市流程的做法一样。
- **清单和阈值**：
  - 场景清单 `Tools/weather/scenarios.json` 列出第 2–7 节验收表的每一行，并标上里程碑。
  - 阈值放在 `Tools/weather/thresholds.json`，做法同 PyPCG 的 `v2_thresholds.json`。
- **能量化的都量化**：
  - **Atmos**：总水量、最大散度、云底高度、迎风与背风的降水比。
  - **风**：固定点探针读数，算背风与开阔处的风速比、阵风到达时间。
  - **树**：改造的 Transform Provider 把每个槽的摆幅、单帧最大转角写进调试缓冲，用来查跳变，以及背风与开阔处的摆幅比。
  - **地表**：采样点上的状态值。比如檐下是干的；路面有积水而草地没有；背风处的雪更厚。
  - **粒子**：被遮挡区域里的雨粒子数，应接近 0。
  - **角色**：湿度和积雪的曲线，与 numpy 模型对照。
  - **换季**：每次换网格都记录"当时是否在视野里"（必须为否）和当帧耗时。
  - **声音**：各场景下 Audio Modulation 总线的值，比如雨声大小、封闭程度。
- **截图要稳**：
  - 固定曝光、固定随机种子、冻结时间（包括云），等几十帧稳定后再拍，截图前关掉编辑器的 CPU 节流（`tl_editor_no_throttle.py`）。
  - 和人工评审通过的基准截图比对，留一定的噪声容差。
- **编辑器注意事项**：沿用项目已有的做法。
  - 一次桥调用只截一张图；
  - 测试期间关掉自动保存，结束时恢复；
  - 编辑器崩溃后，先把 `Saved/Autosaves` 挪开再重开（trap 78）；
  - 尽量不在大关卡之间来回切换（traps 79、83）。

### 8.5 性能

- **采集**：每个 GPU pass 都有自己的统计名（`DECLARE_GPU_STAT` 加 RDG 事件范围），ProfileGPU 里能单独看到。
  spike 里用过的日志解析脚本正式化，输出成表。
- **测试条件**：
  - 固定的相机路径；
  - 每种天气型 × 每个季节；
  - 内部分辨率 1440p；
  - 编辑器不节流。
- **判定**：按 §1.7 按天气状态的预算判定。超出就让测试失败，并指出是哪个 pass。
- **其它记录**：CPU（游戏线程、音频线程）和内存（天气纹理、冬季树网格）也一起记录。

### 8.6 长时间运行和存档

- **长跑**：以 24 倍速跑完一个游戏年（4 季 × 7 天，约 70 分钟真实时间）。检查以下几点：
  - 没有 NaN 或 Inf（调试回读各量的最大值、最小值）；
  - 总水量不失控；
  - 每次换季都完整走完；
  - 内存不增长；
  - 帧时间在预算内。
- **存档**：
  - 在随机时刻存档，包括暴风雨中、换季过渡中。读档后，§1.9 列出的内容都要原样恢复。
  - Atmos 读档后会重新预跑，云相似但不完全相同，这是设计如此。
- **可复现**：同一个种子得到同一串天气，离线和编辑器里都要测。

### 8.7 人工评审

- **截图集**：每个里程碑结束时出一套截图，固定机位，覆盖各天气 × 各季节，交用户看一遍。认可的截图成为基准截图。
- **录音**：每个声音场景用 submix 录几秒，存成 wav，附一张听音清单。
- **原作对照表**：把我们的截图放在视频同一时刻的画面旁边，比如 A 2:07 的调试视图、A 3:54 的雨粒子调试、B 50:36 的干 / 湿 / 积水对比。

### 8.8 日常跑法

| 时机 | 跑什么 | 大约多久 |
|---|---|---|
| 每次改动后 | 离线测试 | 几分钟 |
| 提交前 | 再加 C++ 自动化（两个编辑器都关掉）和冒烟场景集 | 约 10 分钟 |
| 里程碑结束 | 全部场景、性能、一整年长跑、人工评审 | 约 2 小时 |

- **基线不能退**：现有测试保持现在的结果——pypcg 2094 passed / 18 skipped，PyPCGTools 9 个，MCP 17 个。
  M6 改 W7（换 PVE 树、加物候属性）时，pypcg 测试必须保持全过。
- **新套件登记**：新的几套测试和各自的基线，在 M0 写进 CLAUDE.md 的测试表。
