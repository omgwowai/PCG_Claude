## 5. The rotation chain's pivot (the one non-obvious rule)

Every spline the ring/arm chain makes carries **the same data frame translation**:
`(−613.8667464186474, 142.0539320733078, 2800.0000000000146)`, rotation identity. `Transform_Offset`
with `PerPoints` false inverts that frame, applies the yaw to the control points **about the frame's
origin**, and transforms back:

    world' = origin + q_yaw (p − origin)

Rotating any piece of any arm by ±120° (and the base by −60°) about that origin reproduces the
official output to **1e-12 cm on every vertex**; no other pivot candidate (the piece's centroid, its box
centre, the world origin) does. The Z of the origin is irrelevant to a yaw. Both helper and its
fixture test are in `pypcg.geo.frames.rotate_in_frame` / `test_s15_helpers.py`.

The `Transform_Align` rule is equally simple and equally measured: **the whole input set's world box
centre moves to the second input's box centre** (X and Y only; Z untouched because `Justify_Z` is None).
It is a SET operation — `CombinePoints` over every input item — not a per-item shift (`geo.frames.align`).

## 7. Deliberate differences

- `Transform_Align`, `Transform_Offset` (PerPoints false), `Subdivide_Areas_withGrid` and the contracts
  are shared `pypcg.geo` helpers, not copied into the stage.
- The random draws (tree kit, tree scale) run through `ctx.rng` (spec E2) and are compared on counts and
  ranges only (§4).
- `Branch_0`'s `UseMegaplantsTrees` selects the tree assignment inside Python instead of two branches.
- The three footprint parameters are dropped (the shape comes through the volume) — the contract's own
  ruling.

5. **No V2 or V1 run** for the slim graph (it does not exist), so no threshold question was opened; the
