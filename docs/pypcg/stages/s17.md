## 2. The computation

1. **The terrain points** -- `FilterDataByType_0` (Point or Param) keeps the extracted point set. The
   stage takes every `Points` value on its pin; 263 364 points on the demo level, two attributes
   (`None`, `SourcePositions`) it does not use.
2. **Above the sea** -- `AttributeFilter_0` (`$Position.Z`, constant Double threshold, default operator
   `Greater`) and `FilterDataByType_1`: `above()` keeps `loc[2] > SeaLevel` in input order. Measured:
   100 666 points, the same points in the same order as the official node.
3. **The convex hull** -- `FindConvexHull2D_0`: `geo.convex_hull`, a port of the engine's
   `ConvexHull2D::ComputeConvexHull` (Andrew's monotone chain; sort by X then Y; pop on clockwise OR
   collinear; counter-clockwise from the lowest X; three points or fewer pass through). Measured: the
   same 57 indices in the same order as the official node.
4. **The closed linear spline and its control points** -- `CreateSpline_0` (closed, linear) and
   `GetSplineControlPoints_1`: the control points are the hull vertices unchanged (all 57 locations bit
   for bit), each turned toward the NEXT vertex (the spline's tangent; the last toward the first),
   scale 1, box +-1, density 1, steepness 1, seed `ComputeSeedFromPosition` =
   `ComputeSeed(int(x), int(y), int(z))` (`PCGHelpers.cpp:50`). Measured: yaws to 8.5e-14 deg, all 57
   seeds exact. `control_points()`.
5. **The docks** -- `RandomChoice_0` (`Ratio` 0.5152, not fixed mode): `geo.choose(n, DockRatio, rng,
   ceil=True)` -- `CeilToInt(n x Ratio)` docks (30 of 57), kept in hull order, drawn from Python's own
   `ctx.rng` (a new layout, spec E2).
6. **Zero roll and pitch** -- `AttributeMathsOp_3/4`: the control points are built with pitch and roll
   0, so the docks carry yaw only (official zeroed rotators: pitch and roll 0 or 1e-19).
7. **Assign the kits** -- `Subgraph_2 Assign_Assets` (`Assets` = `Dock_A/B_PCG`, `Warehouse_A/B/C_PCG`,
   `PositionOffset` (0, -492.541261, 0), `RotationOffset` 0): one kit per dock with
   `geo.assets.choose` (Python's draw), then `geo.assets.expand_items` -- the primitive's output item for
   item: each dock moved 492.541260 cm along its own local -Y (inland, to the right of its hull edge),
   one point set per kit in first-picked order with the kit's points copied onto each of its docks
   source-major (`Target * Source`), then the moved docks carrying the kit path. The kits come through
   `ctx.ops.assets` (`pypcg.ue.ops.Ops.assets` -> `pypcg.ue.assets.load`), so the module stays pure.

Everything goes to the kept `Spawn_Assets`. **The official graph spawns every pier twice**: its
`Spawn_Assets` spawns each meshed copy AND, from the docks item (whose `Asset` is a kit path), each
dock's kit again -- 19 626 instances = 2 x (9 843 copies - 30 copies whose `Mesh` is the null path).
The port publishes the same items, so the slim graph spawns the same way.

## 3. Deliberate differences

1. **Which docks and which kits** are Python's own random draws (spec E2), so the dock sites and the
   kit mix differ from the official seed's. The counts per seed are fixed (30 docks); the instance
   total follows the kit mix: 20 712 .. 25 702 over the five V2 seeds against the official 19 626.
2. **The dock count rounds UP** (`CeilToInt`, the engine's), not `round(n x ratio)` as the brief says:
   57 x 0.5152 = 29.37 keeps 30 officially. The brief's invariant is stated with the engine's rounding.
3. **The docks do not carry the official control points' `ArriveTangent`, `LeaveTangent`, `InterpType`,
   `None` and `SourcePositions` attributes, nor `dataIndex`**; nothing downstream of the assignment reads
   them (`Spawn_Assets` reads `Asset`). The copies carry every kit attribute (`Material`,
   `RelativeTransform`, ...) as the primitive does.
4. **`Branch_0` and the partition machinery are dropped** with the contract's two parameters;
   `Partitioned` is false on every volume this port runs, so the official graph also takes `Output A`.

## 4. What the `Assign_Assets` helper got wrong, and the fix

Stage 17 is the first stage whose `Assign_Assets` call has several targets with a rotation and an
offset. Against the official primitive (`pyg_probe_t15_tap.py`, all 9 843 copies), Task 12's `expand`
was wrong on four counts its one-target measurements could not see; `pypcg/geo/assets.py` is fixed and
its module docstring records the evidence:

1. the `PositionOffset` / `RotationOffset` / `ScaleOffset` (`TransformPoints_1/2`) apply to the TARGETS
   in their own frame (float offsets), not to the assembly points -- the dump's wiring is
   `FilterDataByType_4 -> TransformPoints_1 -> TransformPoints_2 -> Reroute_0 -> CopyPoints_0.Target`;
2. the output is one point set per kit (first-picked order) plus the moved targets, and inside one kit
   the copies are SOURCE-major (target-major is 2.9 km off on the same data);
3. a kit point whose `Mesh` is the null path stays `"None"` (Task 12 replaced it with the kit path);
4. every output box is rewritten as centre +- half-size x `ExtentsScale` (`AttributeMathsOp_14`).

**Fix round 1 (review of 2026-10-19).** The oracle was run on deterministic official calls of three
more stages, and on stage 17 with settings the oracle graph overrides. It found three more gaps, all fixed:
the primitive's own defaults are `UniformScale` true and `UseMeshBounds` true (Task 12 had false); a
static-mesh asset gives no copy item, only the moved targets (with the mesh's box under
`UseMeshBounds`); and a negative scale takes `FTransform`'s matrix path. What each parameter rests on:

Every row is on disk in `Tools/pypcg/data/assign_oracle_rows.json`. s17 run A = RotationOffset (0, 90, 0),
ScaleOffset (0.2, 1, 1), ExtentsScale (0.7, 1, 1); run D = RotationOffset (pitch 10, yaw -90, roll -20),
ScaleOffset (1.414055, 0.6, 0.7), ExtentsScale (1.2, 0.5, 2), UniformScale and UseMeshBounds false.

| Parameter | Status | Evidence (oracle, exact unless noted) |
|---|---|---|
| `PositionOffset` | measured | s17 `Subgraph_2`; s14 `Subgraph_7` (Z 3), `Subgraph_8` (Z 40) |
| `RotationOffset` | measured | s14 `Subgraph_5` yaw -90 (random ranges zeroed); s17 run A (0, 90, 0) and run D (10, -90, -20) |
| `ScaleOffset` != 1 | measured | s17 run A (0.2, 1, 1) and run D (1.414055, 0.6, 0.7); s15 `Subgraph_20` set to (1.414055, 1, 1) |
| `ExtentsScale` != 1 | measured | s14 `Subgraph_7` (1.2); s17 run A (0.7, 1, 1) and run D (1.2, 0.5, 2); s15 `Subgraph_20` (0.7) |
| `UniformScale` | measured | true and false, above |
| `UseMeshBounds` | measured | true on static meshes (s14 `Subgraph_8`, s15 `Subgraph_20` with `UniformScale`) and on kits (s17); false (s14 `Subgraph_7`, s17 run D) |
| random ranges | derived only | the primitive's `TransformPoints_2` stream is not the port's `ctx.rng` (spec E2); s14 `Subgraph_4` (random) equal on item sizes, order and `Asset` |
| `UseIndexattribute` | not implemented | `expand` ignores it; every official user is also random |
| `MatchScaleToInputBounds`, `UseMeshAttribute` | not measured | no official call sets them |

After the fixes, stage 17's own call is bit for bit on location for all 9 873 points (the matrix
path made the 64 mirrored copies exact) and on the quaternion within 1.1e-16.

`expand` keeps its signature and its merged-points form; `expand_items` is the primitive's own output.
`Points.extend` now carries the engine quaternion column, so a kit merged from several entries keeps
its points' own rotation bits. The `assign` phase of `pypcg_v1_editor.py` now compares the two exactly
(section 5).
