## 2. The two outputs are tagged pass-throughs, not computations

Both published pins are `PCGAddTagSettings` sitting on the output of an engine node:

- `AddTags_1 "Add Tags"` -> `RoadFootprints`, fed by `Subgraph_89 Union All Road Outlines (Road Footprint)`, a `Compose_Areas_Union`. Its content is a **union of outlines**, i.e. a computation the port owns.
- `AddTags_0 "Add Tags"` -> `ModifiedTerrain`, fed by `NamedRerouteUsage_5 "Mesh Terrain Final"` -> `NamedRerouteDeclaration_1` -> `Subgraph_37 Write Terrain (Intersection Flatten)`, a `Write_MeshTerrain`. **That one is a stateful terrain write the contract keeps native.**

Measured on the live demo level (2026-10-16): the stage-7 volume's tagged output is exactly two
items -- `PCGPolygon2DData` tagged `RoadFootprints` (842 714.39 m2, one polygon) and
`PCGMeshPartitionData` tagged `ModifiedTerrain`.

## 3. The footprint branch, as numbered steps

Each step names the official nodes it replaces.

1. **Read the Districts actor** (`Subgraph_0 Get_ActorDataByRef "Districts PCG"`). Its generated
   output is the whole stage-6 tag set: 79 items, of which 57 `localRoads`, 6 `CollectorRoads`,
   4 `ArteryRoads` (measured 2026-10-16).
2. **Split into the three classes** (`FilterDataByTag_3/4/5 "Filter ... Sections (Stripe Pass)"`).
   Each filters with `Operator = Substring`, so the classes are **substring** matches on the tag.
   Two consequences the graph relies on:
   - the closed City outline is tagged `ArteryRoads` (stage 6 publishes the boundary under that tag)
     and reaches the artery pin;
   - the six collector-tagged items are the splitter lines.
3. **Extend each open line by half its class width** (`Intersection_solving`'s
   `Subgraph_1/2/3 Extend ... Road Splines`, each `Transform_Splines_Extend` with
   `distance = <class width>/2`). A closed ring is not extended: `Transform_Splines_Extend`'s
   `InputsProcessing` graph is `InputsProcessing_ForceSpline` and the extension is along the end
   tangents, which a ring does not have.
4. **Outline each line into a ribbon** (`Subgraph_86/87/88 Transform_Outline`, `Width` = that class's
   width). See section 4 for what the CoreProcess actually computes, including the `ForceClosed`
   branch a closed ring takes.
5. **Outline the Landmarks ribbon into the local class** (`Subgraph_86`'s second `PrimaryInput` edge).
   `Subgraph_24 Transform_Areas_Expand(Expand = 800)` over `Subgraph_12` (MainTower) and `Subgraph_1`
   (CentralParkFootprint), then `GetSplineControlPoints_0` -> `CreateSpline_0` (`bClosedLoop`) gives
   the "Landmarks" spline, which is outlined at `local_Width` (`GetGraphParameter_46`).
6. **Union the ribbons** (`Subgraph_89 Compose_Areas_Union` -> `Compose_Areas_Union_CoreProcess`,
   which filters to `Polygon2D` and runs `Polygon2DOperation(Union)`).
7. **Tag and embed the widths** (`AddTags_1` writes `RoadFootprints`; `AddAttribute_2/1/0` write
   `LocalWidth` = `local_Width`, `CollectorWidth` = `collector_width`, `ArteryWidth` = `Artery_width`).

Steps 3 and 5 are what a first reading of the node list misses, and together they are worth 25 % of
the footprint's area: taking the Districts output as open lines only gives -25.5 %, and each of the
two recovers most of that (section 6.1).

Because step 2 reads the **Districts** output rather than the solved sections, the footprint is the
outline union over the districts' own road lines. The naive check agrees: the open lines' lengths
times their widths give 671 302 m2, and the union loses 6.5 % of that to overlaps, which is the
scale a connected road grid implies.

## 4. `Transform_Outline` -- the one thing that had to be measured

The CoreProcess (`Transform_Outline_CoreProcess`, 13 nodes) computes:

```
FilterDataByAttribute_0  keep $IsClosed == false
CreatePolygon2D_2        ForceClosed          <- that filtered output
OffsetPolygon2D_0 / _1   +- width/2          <- CreatePolygon2D_2
Polygon2DOperation_0     Difference           <- grown minus shrunk
CreatePolygon2D_0        ForceOpen, OpenPolygonWidth = width, EndType = Butt
output node              wires BOTH CreatePolygon2D_0 and Polygon2DOperation_0
```

The published output is the **join of two branches**: the `Polygon2DOperation` difference *and* the
raw `CreatePolygon2D_0` band. Which one carries the content depends on the input:

- For an **open** path, `CreatePolygon2D_0`'s `ForceOpen` band is the ribbon, and it is the branch
  that survives. `CreatePolygon2D_2`'s `ForceClosed` ring of an open path is degenerate, both offsets
  of it are empty, and `Polygon2DOperation_0` outputs nothing.
- For a **closed** path, `CreatePolygon2D_0`'s band is the annulus around the ring and
  `Polygon2DOperation_0` is empty for the same reason.

**Measured, 2026-10-16** (`pyg_probe_t10_cal.py`): a 36 118.85 cm straight 2-point path at width 1900
gives a band of exactly `36118.85 x 1900` cm = 6862.58 m2, spanning `+-950` and capped square at both
ends. So `ForceOpen(band)` with `EndType = Butt` is `UE::Geometry::PolygonsOffset` on an open
poly-path (`PCGCreatePolygon2D.cpp:243-269`; `Butt` = "offsets both sides of a path, with square
blunt ends", `PCGPolygon2DUtils.h:24`), and **the ribbon is `width` wide, once**. An earlier reading
that added a `+-width/2` follow-up doubled every ribbon; the engine call makes that unnecessary and
the measurement rejects it.

Wired to the engine as `pypcg.ue.ops.Ops.path_offset` (GeometryScript
`CreatePolygonsFromPathOffset`), which is literally the same `PolygonsOffset` call the PCG node makes.

## 5. Deliberate differences and what is not reproduced yet

1. **`SimpleRoads` is not branched on in the footprint half.** The official graph branches six times
   on `simpleRoads`, but the footprint's `Stripe Pass` filters are fed from `NamedRerouteUsage_2`
   (Districts) directly, ahead of every `simpleRoads` branch, so the footprint does not depend on it.
   The parameter is kept so the slim graph carries it for the kept grammar nodes, and
   `test_simple_roads_produces_one_class_only` pins that changing it does not change the footprint.
2. **The landmark ring's vertex set is passed through whole.** `GetSplineControlPoints_0` ->
   `CreateSpline_0(bClosedLoop)` rebuilds the Landmarks spline from the expanded ring's vertices, and
   the port uses the ring it computed rather than re-reading the engine node's own vertex list. This
   was commit 1's leading candidate for the footprint's -0.65 % and it was **not** the cause (section
   7: a `_along` bug was). Note that `Extract_Segments` is **not** a difference here: it is on the
   sections branch (`Subgraph_3` -> `Gather_0` -> `Subgraph_2`), not the footprint's.
3. **The `$*` attributes** the footprint carries: the official pipeline writes `LocalWidth`,
   `CollectorWidth`, `ArteryWidth` through `PCGAddAttributeSettings`, whose `OutputTarget` is
   `@data.LocalWidth` etc. -- per-*data* attributes on the Polygon2D, not per-vertex. The slim graph
   keeps the three `AddAttribute_*` nodes, so the attributes come from the engine nodes, not Python.

   **The output node must source `AddAttribute_0`, not `AddTags_1`.** The official chain is
   `AddTags_1 -> AddAttribute_2 -> AddAttribute_1 -> AddAttribute_0 -> output`, and the published
   polygon's three attributes only exist because the output hangs off the END of that chain. The 10b
   first pass sourced it from `AddTags_1` and published a polygon with no widths -- which nothing in
   the suite caught, because `checks/s07.py` asserts the tag and the contract test only asks that the
   pin is wired somewhere. Both now have a graph-level guard
   (`test_the_three_width_attributes_reach_the_output_node`), and the count of attributes on the
   generated output matches the official's: **3**.
4. **`Crosswalks` and the two `Write_MeshTerrain` stay native** by contract (Ruling 2), so the 75-node
   Crosswalks primitive and the terrain writes are not ported. The `Crosswalks` node reads
   `Crosswalk_distance_from_intersection = 250` (its own override) and the three road widths.
5. **The terrain half is native end to end** (section 8), so `ModifiedTerrain` is published from the
   two kept `Write_MeshTerrain` nodes exactly as the official graph does it. It is present on every
   run.

## 7. The footprint's residual: closed, and it was the same `_along` bug

Section 7 of commit 1 read: *"The footprint is -0.65 % from the official area offline and -1.61 % in
the V2 run, with `maxX` 109 013.9 against the official 109 548.2 (534 cm short)"*, and listed three
untested candidates (the landmark ring's vertex set, its start vertex, and the ribbon width applied to
it). **None of the three was the cause.** The residual was a bug in the sections half's arclength
helper, reached by the footprint through the landmark ribbon:

`pypcg.geo.sections._along` maps a clip's end point back to an arclength position on the original
path. It returned the arclength of the **nearest vertex**. A clip's ends lie *on* the path but are
usually not its vertices -- `clip_path` inserts the crossing point into the piece -- so on a 2-point
road both ends of a span snapped to the same end of it and every span came back **zero-length**. On
the sections side that emptied 71 of the local inside pieces; on the footprint side it silently
dropped stretches of the landmark ring's segments from the local class. `_along` now projects each
point onto every segment and interpolates; `Saved/t10/t10b_sections_table.txt` carries the before and
after for all four outputs.

Measured after the fix, same live demo inputs, same official run:

| | official | slim |
|---|---|---|
| `RoadFootprints` area | 842 714.39 m2 | **842 845.81 m2** (+0.016 %) |
| bbox | (-122 801.05, -86 813.06) .. (109 548.24, 100 038.05) | **identical to 1e-10 cm on all four edges** |
| sections local / collector / artery | 478 / 68 / 171 | 434 / 90 / 217 |
| `IntersectionsPlanar` | 162 | 167 |

So the 534 cm and the 0.65 % are gone, and the "the official is about 370 cm beyond what this
landmark ribbon can reach" argument that section 7 built is resolved: it *was* reachable, once the
ribbon's own geometry stopped being dropped.

**The two construction facts stay, and they were measured the hard way:**

- the closed City outline is part of the footprint. `FilterDataByTag_5`'s substring match puts it on
  the artery pin, and `Transform_Outline`'s CoreProcess outlines a closed ring on its `ForceClosed`
  branch (`CreatePolygon2D_2` -> `OffsetPolygon2D(+-width/2)` -> Difference). Including it takes the
  union from -25.5 % to -4.25 %;
- the Landmarks ribbon belongs to the local class. `Subgraph_86` is the only outline node with a
  second `PrimaryInput` edge, its `Width` is `local_Width`, and the expanded CentralPark ring reaches
  x = 108 228. Including it takes the union from -4.25 % to -0.65 %.

Both are still required; the -0.65 % they left was the bug, not their residual.

Nothing in this section was a threshold change, and nothing is now: the footprint's area check is a V2
metric against the official value, and every gap recorded here was fixed in the port rather than
absorbed by `v2_thresholds.json`.

## 9. Commit 2, the sections half

### 9.1 What it is

`pypcg/geo/sections.py` (no `unreal` import) is `Intersection_solving`, read out of the primitive's own
IR (`Saved/t10/is_table.txt`) and the embedded `Loop_0` body. Eight steps, each naming the official
nodes it stands for -- the module docstring lists all eight; in shape: extend each class by half its
width, outline each class plain, build the expanded intersection planes from the pairwise overlaps,
build the cutter (artery whole + collector-minus-artery + local-minus-both), run each class through the
`+-Y` dance to make the three ribbons the cutter is made of, cut each class's lines by the cutter in
both directions, split at `roadSectionLimit` and label, then union the short and inside data into
`IntersectionsPlanar`.

The two directions of the one primitive (`Compose_Spline_Cut` = `ClipPaths`) had to compose
differently, and getting that wrong was this slice's largest single cost:

- **Difference** removes what the rings hold, so the clips are applied **one ring at a time**, each fed
  the previous call's output.
- **Intersection** keeps what any ring holds, so it clips **per ring and merges along the arclength**.
  Chaining it would empty the result at the first ring a path misses, which for a road and 334
  scattered planes is every path; concatenating the per-ring pieces would count an overlapping stretch
  of road twice.

### 9.2 Measured against a live oracle

The oracle is `/Game/PyPCG/Probe/PCG_T10bOracle`, a probe graph that runs the official
`Intersection_solving` node verbatim on the demo level's own road inputs and publishes its four
outputs (`pyg_probe_t10b_oracle.py`). The port is fed the same inputs
(`Tools/pypcg/data/s07_sections_input.json`, 79 Districts items) and compared
(`pyg_probe_t10b_count.py`; the full table is `Saved/t10/t10b_sections_table.txt`):

| | oracle | port | delta | port before the fix |
|---|---|---|---|---|
| `LocalSections` | 478 / 24 677.9 m | 434 / 23 404.9 m | -9.2 % count, -5.2 % length | 257 / 21 795.6 m |
| `CollectorSections` | 68 / 2 700.2 m | 90 / 2 708.4 m | +32 % count, +0.3 % length | 34 / 2 462.4 m |

| `IntersectionsPlanar` | 162 | 167 | +3.1 % count | 100 |

#### The bug this comparison found, and it was the whole story of the first pass

`_along(pt, path, cum)` maps a clip's end point back to an arclength position on the original path.
It returned the arclength of the **nearest vertex**. A clip's ends lie *on* the path but are usually
not its vertices -- `clip_path` inserts the crossing point into the piece -- so on a 2-point road both
ends of a span snapped to the same end and every span came back **zero-length**. On a 2-point path
with a ring through its middle, `_union_spans` returned `[(0,0), (0,0)]` and the piece vanished.

Measured consequences before the fix: 71 of the port's 87 local inside pieces were exactly that, each
carrying 0.0 m; 257 local / 34 collector / 185 artery sections against the oracle's 478 / 68 / 171;
and -- the reason this was worth chasing -- the **footprint** was silently missing geometry too,
because the same helper is on the path the landmark ribbon's segments take (section 7).

The fix is one function: `_along` now projects the point onto every segment and interpolates. It
moved every class, published **zero** zero-length sections where the port previously published 87,
took the slim footprint from -0.65 % to +0.016 % with a bbox exact to 1e-10 cm, and took the V2
instance median from 268 623 to 275 523. No threshold moved.

#### What remains: the local class's LENGTH, and it goes missing upstream of the cut

This is the lead, and the counts are a consequence of it rather than the cause. Two observations fix
which side of `Intersection_solving` the divergence is on:

1. **The classes that match on length are the ones the cut made work for.** Artery +0.02 %, collector
   +0.3 % -- both essentially exact. Only the local class is short, by 5.2 % (2 273 m).
2. **The oracle's local total exceeds the port's entire extended local input.** 24 677.9 m against
   23 403.5 m: **+1 274.4 m more than the port has to give**, before anything is cut. A cut cannot
   lengthen its input, so the port is either feeding the primitive less local road than the official
   does, or `Gather_0` contributes more than the port's two inputs (`Subgraph_28 Clip Local Roads At
   Landmark` plus `Subgraph_3`'s segments). The candidates are `Gather_0` and the three landmark clips
   (`Subgraph_27/28/13`).

**That, not the cutter, is where the next task should look.** The `+-Y` cutter geometry and the
granularity of `ClipPaths` are *not* implicated by the length evidence -- they redistribute length
between the outside and inside sets, which is why the count ratios can run +27 % on the artery while
its length matches to 0.02 %.

Three candidates were tested and **ruled out**, each with a measurement (all re-checked after the
fix):

1. **Slivers.** No piece under 1 cm survives now; the mass sits in 1 km+ pieces (local 212 outside /
   219 inside). The oracle has 422 of its 478 local pieces over 1 km.
2. **The expansion unit.** Sweeping `intersection_expansion_range` over 50 / 500 / 5000 cm gives
   planar 235 229 / 310 350 / 626 774 m2 and section counts 257/34/185, 242/29/133, 122/6/50 -- no
   value lands on the oracle's 478/68/171, so the expansion range is not the missing knob

### 9.6 The fix round (10b review)

Two Important findings, both accepted. Neither was a code-behaviour change to the sections geometry.

**The -3.8 % was attributed to the wrong mechanism.** The first pass's note and commit message said
"fewer, longer sections means fewer spawn points" and pointed the next task at `sections.py`. The
arithmetic contradicts that and is now in section 6.2 in full: the port's total section length is
36 808.7 m against the oracle's 38 071.0 m (-3.32 %), instances are -3.78 %, and per metre the two
sides are 7.485 against 7.522 -- **0.49 % apart**. `Place_OnSpline` places by distance, so splitting
a metre of road into two sections adds essentially nothing; the instance deficit tracks the length
deficit 1:1. The count ratios even run the other way: the port's artery has +27 % more sections than
the oracle's and its collector +32 %, while both match on length to 0.02 % / 0.3 %.

The correction matters because it moves the next task to the **other side of the cut**. The oracle's
local total (24 677.9 m) exceeds the port's whole extended local input (23 403.5 m) by 1 274.4 m
before anything is cut, and a cut cannot lengthen its input -- so the candidates are `Gather_0` and
the three landmark clips (`Subgraph_27/28/13`), not the `+-Y` cutter or `ClipPaths`' granularity.
Sections 6.2, 9.2 and 10 now say that, and section 10 names it first.

**The published `RoadFootprints` was losing its three width attributes.** `g.out(...)` takes no
destination -- it writes every argument as an edge to the output node's `Out` pin -- so
`g.out(g.py['RoadFootprints'], _n['AddTags_0']['Out'])` ended the footprint chain at `AddTags_1` and
left `AddAttribute_2/1/0` wired only to each other, consumed by nothing. The official output node
sources `[AddAttribute_0, AddTags_0]`. The consequence: the published polygon carried no
`LocalWidth` / `CollectorWidth` / `ArteryWidth`, while section 5 claimed the kept `AddAttribute_*`
nodes supplied them -- and stage 10 reads `@data.ArteryWidth` off that polygon to size its sidewalk
expansion (stage 18 reads it too). Neither is ported yet, so nothing caught it.

Fixed to `g.out(_n['AddAttribute_0']['Out'], _n['AddTags_0']['Out'])`, with `g.py['RoadFootprints']`
still feeding `AddTags_1`. Verified end to end on the demo level: the generated slim polygon's
`PCGMetadata` reports **3** attributes, the same as the official graph's polygon. A graph-level test
(`test_the_three_width_attributes_reach_the_output_node`) now asserts the output node is sourced from
the artery-width node and that the three form one chain into it; **reverting the fix makes that test
fail** (checked), and it did not exist before, because `checks/s07.py` asserts the tag and the
contract test only asserts the pin is used somewhere.

A binding limit found while verifying, worth recording: **`PCGMetadata.get_attributes()` hands Python
empty arrays through this build.** `get_attribute_count()` returns 3, but the `(names, types)` tuple
comes back as two zero-length `Array` objects, so the attribute *names* cannot be read from Python --
only the count. That is why the end-to-end check above asserts the count against the official's, and
it is why a name-level assertion lives in the offline graph test instead.

Two minors also fixed: `_class_lines`' unused `width_cm` parameter is gone (the decal lines are width-
independent by construction -- `FilterDataByTag_6/10/11` sit ahead of `Subgraph_1/2/3`), and the
`Spline` construction's forced Z is now one helper (`_xyz`), so the unconditional-arity pattern
`plane.py` was just fixed for does not reappear at the stage boundary.
