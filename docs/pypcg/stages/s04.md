# Stage 4 -- MainTowerFootprint (`PCG_2_1_MainTower_Footprint`)

Contract from `docs/pypcg/stages/s04-brief.md`. Official graph: 6 nodes (excluding input/output) --
2 parameter getters, 1 `Create_Spline_Shape` subgraph (52-node CoreProcess), 1 reroute, a
`Transform_Offset` (Z +10 000, feeding only the debug mesh) and the debug mesh itself.

## 1. Contract

| | |
|---|---|
| Inputs | none in the official sense; the volume's own transform arrives as one point on the `Volume` pin (`Get Actor Data`, `Mode = GetSinglePoint`) |
| Outputs | `Footprint` -- one closed, linear, 6-vertex spline |
| Parameters | `RectWidth` 16000 (Float), `RectLength` 16000 (Float) |
| Dropped | `NewProperty` 8000 -- no getter reads it; `Subgraph_0` (`Debug_PrimitiveData`); `Subgraph_1` (`Transform_Offset`, Z +10 000, feeds only the debug mesh) |
| Kept generation | none |
| Output tags | the official output carries `Primitive:CreateSplineShape` and `Type:ClosedSpline`; the slim node's output carries `Footprint` (see section 5) |
| Downstream | stage 7 (`Transform_Areas_Expand`, half the local road width), 9 (landmark exclusion), 10 (exclusion + a 300 cm sidewalk setback contract), 13 (undividable-district exclusion), 15 (five `Transform_Align` reads, a 10 m and a 15 m contract) |

## 2. The computation, as numbered steps

1. **Read the volume's own transform** -- `RectMain`'s `GetActorData_1`
   (`PCGDataFromActorSettings`, `Mode = GetSinglePoint`), which the CoreProcess runs *inside* the
   primitive. It yields one point whose translation and rotation are the volume actor's and whose
   scale is the actor's own (25, 25, 10 in the demo). The slim graph runs the same node and delivers
   its output on the `Volume` pin; **what arrives there is spelled out in section 5, and every later
   stage that publishes a shape from its own transform should copy it.**
2. **Build the polygon** -- `RectMain` (`Create_Spline_Shape`, overrides `Ngon` 6, `Linear` true,
   `AtWorldOrigin` false; `Width`/`Length` overrides of 5000 are dead because both pins are wired to
   `GP_Width`/`GP_Length`). Inside `Create_Spline_Shape_CoreProcess` (52 nodes), `Ngon == 4` fails,
   so the sphere branch runs: `CreatePointsSphere_0` with `LongitudinalSegments = Ngon` (6) and both
   latitude angles 0 puts 6 points on a circle of radius `Width x 0.5` (`AttributeMathsOp_1`,
   `DefaultValue2` 0.5 -- the first vertex at angle 0 is `(Width/2, 0)`); `FindConvexHull2D_0` keeps
   them; `AttributeMathsOp_0` zeroes `$Rotation.Roll`; `MakeTransformAttribute_2` builds a scale of
   `(1, Length / Width, 1)` (`MakeVectorAttribute_1`: X and Z from `CreateConstant_0`, Y from
   `AttributeMathsOp_2` = Length / Width); `AttributeTransformOp_3` applies that scale.
3. **Place it at the volume** -- `AttributeTransformOp_2` composes the shape with
   `MakeTransformAttribute_1`: translation and rotation from `GetActorData_1`, scale from the
   unconnected `mult` pin, i.e. (1, 1, 1). **The actor's own scale (25, 25, 10) is not used.** With
   `AtWorldOrigin` false the shape takes `Branch_4`'s A side, so the volume's transform is applied;
   true would skip it.
4. **Winding** -- `CreateSpline_1` (closed, linear) then `SplineDirection_0`
   (`ForceCounterClockwise`). Traps.md 41: UE's "counter-clockwise" force leaves a **negative**
   standard shoelace area, and the measured official hexagon has exactly that order.

So the hexagon is `N = 6` points on a circle of radius `RectWidth / 2`, stretched along local Y by
`RectLength / RectWidth`, then turned by the volume's yaw about the volume's location. As a point
set that is `geo.ngon(center, RectWidth / 2, 6, start_deg=-60, step_deg=-60, ...)`, but **the port
does not call `ngon`**: it computes each vertex as `-(R cos p, R sin p)` at `p = 120 - 60k` degrees,
which is the engine's own arithmetic and reproduces the official doubles bit for bit (section 4 says
why the last bits matter).

**The vertex order is measured, not derived from `CreatePointsSphere_0`'s own `0 .. 360` sweep.**
The measured official sequence begins at `(R/2, -R*sqrt(3)/2)` -- local angle -60 -- and runs
clockwise; a sweep starting at 0 does not reproduce it in any step direction (every vertex 8000 cm
off, measured offline), so something between the sphere and the output re-bases the list --
plausibly the convex hull's own vertex order, which was not reproduced node for node. Z is the
volume's Z (the demo volume sits at Z 0, so the official graph never shows one).

## 3. Deliberate differences

1. **`RectWidth` is the sphere's diameter**, i.e. twice the radius `CreatePointsSphere_0` builds on:
   the six vertices sit `RectWidth / 2` from the centre at the two that lie on the local X axis. At
   the official ratio 1 the hexagon is regular, so `RectWidth` is also its widest corner-to-corner
   span (16 000) and its flat-to-flat width is `RectWidth x sqrt(3) / 2` = 13 856.4. **At any other
   ratio neither of those readings survives**: the four off-axis vertices sit at
   `R sqrt(1/4 + 3 r^2 / 4)` (with `R = RectWidth / 2`, `r = RectLength / RectWidth`), so the widest
   span is `R sqrt(1 + 3 r^2)` and there are two distinct vertex radii, `R` and that one. The
   parameter's official tooltip ("Width of the landmark rectangle") predates the shape being a
   hexagon; the number to expose is the one the node reads.
2. **`RectLength` is a ratio, not a size.** It enters only as `Length / Width` on local Y. At the
   official 16000/16000 it is 1 and the hexagon is regular, which is why the demo cannot distinguish
   "a ratio" from "a side". The stage keeps the official semantics so that changing RectLength alone
   reproduces what the graph would do.
3. `Subgraph_1` (`Transform_Offset` Z +10 000) is dropped: its consumer is the debug mesh.
4. The output carries `Footprint` instead of the primitive's `Primitive:CreateSplineShape` /
   `Type:ClosedSpline` tags. No downstream stage filters on either (stage 7 filters `Roads` content
   and reads this volume by role), and V2 compares by contract tag.

## 4. What could not be reproduced

Nothing at the demo's transform. **The port's six vertices equal the official ones bit for bit**, and
that turned out to be required, not cosmetic (review round 2, 2026-10-19):

- The first port built the hexagon with `geo.ngon(R, 6, -60, -60)`: the same points to 2.9e-12 cm,
  but different last bits (`4000.000000000001` where the engine has `3999.999999999998`). Stage 15
  (`PCG_4_1_MainTower_Visuals`) is deterministic -- two official runs give 35 239 instances both
  times -- and on that footprint it published **35 008 (-0.66 %)**, the difference all in its
  rooftop props and one wall mesh. Feeding the slim graph the official doubles verbatim gave 35 239,
  which isolated the cause to the coordinates' last bits; tags (`Type:ClosedSpline`,
  `Primitive:CreateSplineShape`) and the per-point rotations, tested one at a time, changed nothing.
- The engine's own arithmetic, recovered offline from the six measured doubles: vertex k is
  `-(R cos p, R sin p)` with `p = 120 - 60k` degrees and `math.radians(p)` -- the sphere's longitudes
  normalised into [-180, 180) and negated. `hexagon()` now computes exactly that, then the Y stretch,
  then (only at a non-zero yaw) `geo.rotate`, then the translation. At the origin with yaw 0 every
  step after the first is exact, so the output equals the official doubles; stage 15 then publishes
  35 239 with an identical per-mesh table.
- The official spline points also carry a per-point rotation, yaw 30 / -30 / -90 / -150 / 150 / 90
  (the sphere's tangential orientation, `p - 90` plus the volume's yaw). The port now writes it
  (`geo.Spline.rotations`, written by `convert._spline_data`); it is not what stage 15 reads, but it
  is part of the published data and costs nothing.

**What is not proven bit-exact:** a volume turned by a non-zero yaw. The engine turns the points
with the actor's quaternion after rotator round trips the port cannot see, and `geo.rotate` agrees
with it to ~1e-11 cm, not to the bit -- stage 5's park (yaw 34.22 deg) is the measured case: 3 of its
8 coordinates match bit for bit, the worst is 1.6e-11 cm off. Any stage whose downstream reads such a
footprint can show the same last-bit sensitivity stage 15 did.

The re-basing of the vertex list (the sphere sweeps `0 .. 360`, the published list starts at 120 and
negates) is matched from measurement, not traced node for node.

## 5. The volume point: what `inputs["Volume"]` actually holds

This is the reusable contract for every stage that publishes a shape from its own transform. Measured
2026-10-17 from `Saved/PyPCG/runs/s04.json` and `s05.json` -- the run records are written from the
values the stage received -- and cross-checked against each volume actor's transform
(`pyg_probe_t13_delta.py`).

`inputs["Volume"]` is a **list of `(value, tags)` items**: one item, no tags. The value is a
**`pypcg.geo.Points`**, not a transform and not a single `Point`, with **exactly one point**:

| column | content |
|---|---|
| `loc[0]` | the volume actor's **world** translation |
| `rot[0]` | `(pitch, yaw, roll)` in degrees -- so the **yaw is `[1]`** |
| `scale[0]` | the actor's **own scale** -- see the warning below |
| `attrs["ActorReference"]` | the volume's soft object path (`SoftObjectPath`) |
| `bounds_min` / `bounds_max` | `±100` cm (the point primitive's box) |

`pypcg.stage_api.volume_point(inputs)` is the one implementation: it returns `(loc, yaw)` or
`(None, 0.0)` for an empty pin, and both stages and both V1 checks call it.

**The actor scale must NOT be applied.** Both official primitives take only translation and rotation
from `GetActorData_1` and build their own scale -- stage 4 `(1, Length/Width, 1)`, stage 5
`(1, 1, 1)` (the `mult` pin is unconnected). The demo volumes carry scale (25, 25, 10) and
(500, 100, 10); a port that multiplied by `scale[0]` would publish a 25x tower and a 500x park, and
its first V2 run would show it as a footprint 25 times too large.

A note on the two shapes' Z: stage 4 keeps `loc[2]` as the output Z (the demo volume sits at Z 0, so
the official graph never shows one), while stage 5 pins Z 0 -- `AttributeMathsOp_0` in its graph, and
its volume sits at Z 9950 with an official output at Z 0. A stage that copies the read should decide
its Z from its own official graph, not from this one.
