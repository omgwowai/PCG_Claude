# Stage 3 -- BG_Mountains (`PCG_1_3_BG_Mountains`)

Contract from `docs/pypcg/stages/s03-brief.md`. Official graph: 7 nodes (excluding input/output) --
`PCGLoadDataAsset_0` (the `VistaCliffs_PCG` data asset), `CreatePoints_0`, `CopyPoints_0`, three
`PCGMetadataMathsSettings` and `StaticMeshSpawner_0`. The official output node is **unwired**.

## 1. Contract

| | |
|---|---|
| Inputs | `Cliffs` -- the `VistaCliffs_PCG` points (kept `PCGLoadDataAsset_0`): 60 points, one of them the asset's root at the origin with a null `Mesh`; 7 attributes (`Mesh`, `Material`, `SkeletalMesh` soft paths, `HierarchyDepth`, `ActorIndex`, `ParentIndex` Int64, `RelativeTransform`) |
| Outputs | `Points` -- the stamped cliff points, fed to the kept `StaticMeshSpawner_0` and to the graph output |
| Parameters | `AnchorZ` **-50 000**, `AnchorScaleXY` 1.75, `AnchorScaleZ` 0.5, `ZMin` -100 000, `ZMax` 100 000 (all new: the official graph exposes no parameter) |
| Kept generation | `StaticMeshSpawner_0` (mesh selector by attribute `Mesh`) |
| Output tags | none in the official graph (nothing reaches its output); the Python output carries `Points` |
| Downstream | none |

**`AnchorZ` is not the brief's 0.** The official anchor (`CreatePoints_0`) is translation
(0, 0, **-50 000**), scale (1.75, 1.75, 0.5); the brief's own algorithm line says so, its parameter
row does not. The default is the official value, so `AnchorZ` is exactly the "+ AnchorZ" of the
invariant `Z = clamp(source Z x AnchorScaleZ + AnchorZ)`.

**The graph output.** The official graph publishes nothing; the contract lists `Points` as an output,
so the slim graph wires the Python `Points` to the output as well as to the spawner. Nothing reads it.

## 2. The computation, as numbered steps

1. **The anchor** -- `CreatePoints_0`: one point, translation (0, 0, `AnchorZ`), identity rotation,
   scale (`AnchorScaleXY`, `AnchorScaleXY`, `AnchorScaleZ`), seed 0.
2. **The stamp** -- `CopyPoints_0` (Relative rotation / scale / colour / seed, `AttributeInheritance`
   `SourceOnly`). PCGCopyPoints.cpp:346-372: `Out = SourceTransform * TargetTransform`, which with an
   identity target rotation is location `source x target scale + target translation` (the identity
   quaternion rotate is exact), scale `source scale x target scale`, rotation the source's; colour
   `source x (1,1,1,1)`; seed `ComputeSeed(source seed, 0)`; every source attribute carried.
3. **Roll and pitch** -- `AttributeMathsOp_0` (`Set $Rotation.Roll` to 0) and `AttributeMathsOp_1`
   (`Set $Rotation.Pitch` to 0): the port writes rotation `(0, source yaw, 0)`.
4. **The clamp** -- `AttributeMathsOp_2` (`Clamp $Position.Z`, pin defaults -100 000 / 100 000):
   `max(ZMin, min(Z, ZMax))`. 5 of the 59 cliffs hit the upper bound (none the lower) at the demo values.
5. **The spawn** -- kept: `StaticMeshSpawner_0` reads the Python `Points` and selects each mesh by its
   `Mesh` attribute (the root point's null mesh spawns nothing).

## 3. Deliberate differences

1. The rotation is written as a rotator `(0, yaw, 0)` through `convert`, not as the maths nodes'
   rotator-to-quaternion round trip. The spawned instances' yaw differs from the official by at most
   **5.8e-6 degrees (1.0e-7 rad)**. That is a magnitude argument, not a "nothing reads it" one: the
   largest cliff's local bounds are +-28 888 x +-18 499 cm and its instance scale reaches 40, so the
   farthest corner is 1.37e6 cm from the pivot and the yaw error moves it by 1.0e-7 x 1.37e6 =
   **0.14 cm**, below float precision at that distance in world space. Locations are identical to the
   last bit, scales agree to 7e-14.
2. The Python output carries the tag `Points` and is also published on the graph output (section 1).

## 4. What could not be reproduced

Nothing. The trap "`PCGMetadata.get_attributes()` returns empty arrays" did not bite here: on the
`VistaCliffs_PCG` point data `convert` reads all 7 attribute names and types (probe
`pyg_probe_t14_cliffs.py`, 2026-10-19), and `Mesh` survives the round trip (V2's 59 instances on the
right mesh).

**The fixtures.** Two files under `Tools/pypcg/data/`, both written by the committed generator
`Content/Python/pypcg_cliffs_fixture.py` (read-only: it generates nothing and saves nothing):

- `s03_vista_cliffs.json` -- the data asset's 60 points; the stage's input for the tests and the V1
  check;
- `s03_official_instances.json` -- the 59 instance transforms the OFFICIAL graph's
  `StaticMeshSpawner_0` placed in the demo level: the stage's offline oracle
  (`test_stamp_matches_the_official_spawners_instances` compares the stamp with it directly).

To regenerate both: leave the stage-3 volume on its official graph and generated (right after V2's
`restore` is fine), then `run_unreal_script("pypcg_cliffs_fixture.py", {})` and re-run the offline
suite. Regenerate only when the data asset or the generation layer changes.
